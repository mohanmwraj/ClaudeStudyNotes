# 50 Instant Red Flags in Java and Spring Pull Requests

> **What this module is.** The minute-2 radar for Java 21+, Spring, Hibernate, Kafka, Beam and AI-serving code, as 50 patterns you can see in a diff before you understand it. Each flag gives the smell, why it causes outages, the one question to ask, the fix, and where this KB proves it with compiled code. Each flag also says whether a regular expression can find it. `redflags.py` implements every greppable flag and runs over all eight Java PRs in this KB. Its results set the honest expectation: grep points at most planted defects, but it can't see a sixth of them, and it keeps raising flags on the corrected code.

A defect counts as *flagged* when a rule fires on the line its answer key cites. The rules were written alongside these PRs, so the flagged count is an upper bound, which this sheet states wherever it uses the number. ## 0. Orientation

### 0.1 How to use this sheet in a live round

1. **Minute 2:** skim the diff for the *smells* below. Each hit is a question, not a verdict. Write the question next to the line.
2. **Minute 10:** answer each question with one hop of context: the caller, the config, the unchanged line above the hunk.
3. **Minute 20:** keep the ones whose answers are bad, rank them by blast radius, and write the comments (see 01-03 for tone).

The flags are grouped by *mechanism*, not by framework:

| Group | Flags | The question underneath |
|---|---|---|
| A. Transactions and proxies | J01–J06 | What is actually inside the transaction, and when does it end? |
| B. Data and JPA | J07–J13 | Is this value valid, and how many rows, queries and identities does it touch? |
| C. Concurrency | J14–J21 | What does each thread hold, for how long, and who stops it? |
| D. Remote calls, time and locks | J22–J28 | What happens when the other side is slow, repeats, or is wrong about time? |
| E. Kafka and Beam | J29–J38 | When is "processed" recorded, and what identity deduplicates? |
| F. Security and tenancy | J39–J44 | Who chose this value, and whose scope does it carry? |
| G. AI serving and agent tools | J45–J50 | What can the model reach, and what survives a retry or a cancel? |

## 1. First principles

1. **A red flag is a question.** `synchronized` is fine around a counter and an outage around an HTTP call. The flag tells you where to look, and the context tells you whether it's a bug.
2. **Lifecycles beat syntax.** Most Sev-1s here are about *when* something ends: a transaction, a stream, a lease, an offset, a cache entry. Ask "what is the full lifetime of this resource, and who ends it on the failure path?"
3. **Scope is a security property.** Tenant, user, groups and filters must flow from authenticated sources into every query, cache key and tool call.
4. **Repetition is the default.** Retries, redeliveries, rebalances and agent re-plans mean every side effect runs twice eventually. Idempotency is a design requirement, not an optimization.
5. **Unchanged lines matter.** Several defects in this KB are completed by a line the diff doesn't touch: a capacity constant, a shared annotation, a deleted setting. Read one screen above and below each hunk.
6. **Tools cost attention.** The scanner's false alarms are as real as its hits. Use automated flags to *direct* review, never to replace it.

## 2. The 50 flags

Legend: **[grep]** means `redflags.py` has a rule with this id. **[judgment]** means no reliable regex exists, so you find it by reading.

### A. Transactions and Spring proxies

#### J01 · A proxy annotation on a method called from its own class [grep]
**Smell.** `@Transactional(propagation = REQUIRES_NEW)`, `@Async` or `@Cacheable` on a method that the same class calls as `this.method()`. **Why.** Spring applies these through a proxy, and self-invocation bypasses it, so the annotation silently does nothing: no new transaction, no async, no cache. **Ask.** "Does this call go through the proxy?" **Fix.** Move the method to another bean, or call through an injected self-reference or a `TransactionTemplate`. **Seen in:** [PR01 F1](../02-Java-Spring-Hibernate-and-Microservices-PR-Simulations/01-pr01-fintech-wallet-transfer-transactional-proxy-and-deadlock-traps.md).

#### J02 · A checked exception thrown out of a `@Transactional` method [grep]
**Smell.** `@Transactional … throws SomeCheckedException`. **Why.** By default Spring rolls back only on unchecked exceptions and `Error`, so a checked exception *commits* whatever happened before it, such as a debit. **Ask.** "If this throws after the first write, what is committed?" **Fix.** `rollbackFor = Exception.class`, or validate before writing. **Seen in:** [PR01 F2](../02-Java-Spring-Hibernate-and-Microservices-PR-Simulations/01-pr01-fintech-wallet-transfer-transactional-proxy-and-deadlock-traps.md).

#### J03 · Row locks taken in request order [grep]
**Smell.** `lockForUpdate(from)` then `lockForUpdate(to)`, or `SELECT … FOR UPDATE` in caller-determined order. **Why.** Two opposite requests lock A→B and B→A and deadlock. The database kills one, and the retry storms. **Ask.** "Is there a global lock order?" **Fix.** Lock by ascending id, or use a single statement. **Seen in:** [PR01 F3](../02-Java-Spring-Hibernate-and-Microservices-PR-Simulations/01-pr01-fintech-wallet-transfer-transactional-proxy-and-deadlock-traps.md).

#### J04 · A remote call inside a transaction [judgment]
**Smell.** An HTTP or gRPC client call between `@Transactional` start and commit, or between `begin()` and `commit()`. **Why.** The row locks and the pooled connection are held for the remote call's latency. When the remote side slows down, the pool drains and every endpoint fails. **Ask.** "What does this transaction hold while it waits?" **Fix.** Call before (or after) the transaction; keep transactions to local work. **Seen in:** [PR01 F4](../02-Java-Spring-Hibernate-and-Microservices-PR-Simulations/01-pr01-fintech-wallet-transfer-transactional-proxy-and-deadlock-traps.md), [PR02 F3](../02-Java-Spring-Hibernate-and-Microservices-PR-Simulations/02-pr02-high-throughput-order-api-n-plus-1-connection-exhaustion-and-virtual-threads.md).

#### J05 · `@EventListener` for side effects of a transaction [grep]
**Smell.** `@EventListener` handling an event published inside a transaction. **Why.** It runs synchronously *before commit*: notifications go out for work that then rolls back, and a slow listener holds the transaction. **Ask.** "Should this happen if the transaction rolls back?" **Fix.** `@TransactionalEventListener(phase = AFTER_COMMIT)` (or an outbox). **Seen in:** [PR01 F5](../02-Java-Spring-Hibernate-and-Microservices-PR-Simulations/01-pr01-fintech-wallet-transfer-transactional-proxy-and-deadlock-traps.md).

#### J06 · Idempotency checked last [judgment]
**Smell.** The idempotency key is inserted at the end of the operation, after the side effects. **Why.** A retry redoes every side effect and *then* fails on the unique constraint, after the money has moved twice. **Ask.** "What does a retry with the same key do?" **Fix.** Claim the key first, in the same transaction, and return the stored result on a repeat. **Seen in:** [PR01 F6](../02-Java-Spring-Hibernate-and-Microservices-PR-Simulations/01-pr01-fintech-wallet-transfer-transactional-proxy-and-deadlock-traps.md).

### B. Data and JPA

#### J07 · Money or quantities without sign, unit or currency validation [grep]
**Smell.** `record Cmd(long amount)`, `((Number) x).longValue()`, `amount: number` in a schema. **Why.** Negative values reverse transfers, mixed currencies multiply value, and truncation turns 49.99 into 49. **Ask.** "What are the unit, the range and the currency, and who checks them?" **Fix.** Integer minor units with the unit in the name, `> 0` and bounds checked server-side, and currency compared. **Seen in:** [PR01 F7, F8](../02-Java-Spring-Hibernate-and-Microservices-PR-Simulations/01-pr01-fintech-wallet-transfer-transactional-proxy-and-deadlock-traps.md), [PR11 F7](../05-AI-Engineering-RAG-and-MCP-Server-PR-Simulations/02-pr11-mcp-tool-server-confused-deputy-and-non-idempotent-agent-retries.md).

#### J08 · A "reliable" event written outside the business transaction [judgment]
**Smell.** `outbox.append(...)` (or `publish`) before or after the transaction that changes the state. **Why.** Either half can commit alone: phantom events for failed writes, or lost events for successful ones. **Ask.** "Do the state change and the event commit atomically?" **Fix.** Insert the outbox row in the same transaction as the state change. **Seen in:** [PR06 F1](../03-Kafka-Beam-Dataflow-and-Distributed-Streaming-PR-Simulations/03-pr06-transactional-outbox-and-redis-distributed-lock-fencing-bugs.md).

#### J09 · An association walked inside a loop (N+1) [grep]
**Smell.** `orders.forEach(o -> o.getCustomer().getName())`. **Why.** One query per element: 100 orders make 101 round trips, and latency scales with page size. **Ask.** "How many queries for a page of N?" **Fix.** `join fetch`, an entity graph, or batch fetching, verified with SQL logging. **Seen in:** [PR02 F1](../02-Java-Spring-Hibernate-and-Microservices-PR-Simulations/02-pr02-high-throughput-order-api-n-plus-1-connection-exhaustion-and-virtual-threads.md).

#### J10 · Entity `equals`/`hashCode` on a generated id [grep]
**Smell.** `Objects.equals(id, other.id)` and entities in a `HashSet`. **Why.** New entities all have `id == null` and compare equal, so a `Set` keeps one of them and silently drops the rest. **Ask.** "Are any of these compared before they're persisted?" **Fix.** Use a business key, or identity semantics with a constant `hashCode`; prefer `List` for owned collections. **Seen in:** [PR02 F2](../02-Java-Spring-Hibernate-and-Microservices-PR-Simulations/02-pr02-high-throughput-order-api-n-plus-1-connection-exhaustion-and-virtual-threads.md).

#### J11 · An `EntityManager`, connection or session outside try-with-resources [grep]
**Smell.** `EntityManager em = emf.createEntityManager();` followed by code that can throw. **Why.** The exception path leaks the connection, and the pool runs dry after N failures. **Ask.** "Who closes this when the next line throws?" **Fix.** try-with-resources, or a managed (container) persistence context. **Seen in:** [PR02 F4](../02-Java-Spring-Hibernate-and-Microservices-PR-Simulations/02-pr02-high-throughput-order-api-n-plus-1-connection-exhaustion-and-virtual-threads.md).

#### J12 · An unbounded query into one persistence context [grep]
**Smell.** `select o from Order o` with no `where`/limit, then a loop that modifies everything. **Why.** The whole table loads into memory and one transaction: OOM, a long-held lock, a huge flush. **Ask.** "How many rows in production?" **Fix.** Keyset-paginated batches, each in its own transaction with `clear()`, or a set-based `UPDATE`. **Seen in:** [PR02 F7](../02-Java-Spring-Hibernate-and-Microservices-PR-Simulations/02-pr02-high-throughput-order-api-n-plus-1-connection-exhaustion-and-virtual-threads.md).

#### J13 · A blind `UPDATE` with no version or fence [grep]
**Smell.** `UPDATE t SET x = ? WHERE key = ?` with no version, fencing token or compare. **Why.** A stale writer (a paused node, an expired lease) overwrites newer state, so cursors move backward and counters regress. **Ask.** "What if the writer's view is old?" **Fix.** `WHERE version = ?` (optimistic locking) or a monotonic fencing token. Note that the rule also fires on `join fetch`: check pagination SQL, which PR02 shows is safe on Hibernate 7.4 (decoy D1). **Seen in:** [PR06 F7](../03-Kafka-Beam-Dataflow-and-Distributed-Streaming-PR-Simulations/03-pr06-transactional-outbox-and-redis-distributed-lock-fencing-bugs.md).

### C. Concurrency

#### J14 · An executor per request, or one whose tasks hold scarce resources [grep]
**Smell.** `newVirtualThreadPerTaskExecutor()` fan-out over a list, or `newFixedThreadPool(n)` used for long-lived work. **Why.** Virtual threads are cheap, but what they *hold* (connections, permits) isn't. A fixed pool caps concurrency at N long tasks. **Ask.** "What does each task hold, and for how long?" **Fix.** Bound with a semaphore sized to the scarcest resource; don't hold pooled resources across waits. **Seen in:** [PR02 F3](../02-Java-Spring-Hibernate-and-Microservices-PR-Simulations/02-pr02-high-throughput-order-api-n-plus-1-connection-exhaustion-and-virtual-threads.md), [PR10 F1](../05-AI-Engineering-RAG-and-MCP-Server-PR-Simulations/01-pr10-spring-ai-rag-pipeline-sse-thread-starvation-and-acl-leakage.md).

#### J15 · `synchronized` around slow or remote work [grep]
**Smell.** A `synchronized` method or block containing I/O. **Why.** All callers serialize behind the slowest call. On JDK 21–23 a virtual thread blocking inside `synchronized` pins its carrier, so a few calls can stall the scheduler (JEP 491 removed this pinning in JDK 24). **Ask.** "Is anything inside slow?" **Fix.** Refresh outside the lock (single-flight), or use `ReentrantLock` and a cached value. **Seen in:** [PR02 F5](../02-Java-Spring-Hibernate-and-Microservices-PR-Simulations/02-pr02-high-throughput-order-api-n-plus-1-connection-exhaustion-and-virtual-threads.md).

#### J16 · `ThreadLocal` as a cache [grep]
**Smell.** `ThreadLocal.withInitial(...)` "to reuse" an object. **Why.** With one virtual thread per task, every task creates its own instance, so nothing is reused and memory grows with concurrency. In pools, values leak across requests. **Ask.** "How many threads touch this, and do they live long?" **Fix.** Immutable/thread-safe objects (`DateTimeFormatter`), or an explicit pool. **Seen in:** [PR02 F6](../02-Java-Spring-Hibernate-and-Microservices-PR-Simulations/02-pr02-high-throughput-order-api-n-plus-1-connection-exhaustion-and-virtual-threads.md).

#### J17 · Fire-and-forget `submit` [grep]
**Smell.** `executor.submit(() -> …)` with the `Future` discarded. **Why.** Failures vanish into the `Future`, ordering across tasks is lost, and nothing can cancel the task. **Ask.** "Who sees this task fail, and who stops it?" **Fix.** Keep and observe the future, use per-key serial lanes when order matters, and wire cancellation. **Seen in:** [PR04 F2](../03-Kafka-Beam-Dataflow-and-Distributed-Streaming-PR-Simulations/01-pr04-kafka-consumer-offset-commit-race-poison-pill-and-rebalance-storm.md), [PR10 F2](../05-AI-Engineering-RAG-and-MCP-Server-PR-Simulations/01-pr10-spring-ai-rag-pipeline-sse-thread-starvation-and-acl-leakage.md).

#### J18 · An unbounded retry loop [grep]
**Smell.** `for (int attempt = 1; ; attempt++)` or `while (true)` around a remote call. **Why.** A permanent failure (a poison message, a new event type) retries forever, blocking its partition while lag metrics look healthy. **Ask.** "What stops this loop for an error that will never succeed?" **Fix.** Bounded attempts with classification (retryable or not), and a DLQ. **Seen in:** [PR04 F3](../03-Kafka-Beam-Dataflow-and-Distributed-Streaming-PR-Simulations/01-pr04-kafka-consumer-offset-commit-race-poison-pill-and-rebalance-storm.md).

#### J19 · `InterruptedException` swallowed or restored without stopping [grep]
**Smell.** `catch (InterruptedException e) { Thread.currentThread().interrupt(); }` inside a retry loop, which then continues. **Why.** The restored flag makes the next `sleep` throw at once, so the loop spins hot and never exits, and the pod hangs on SIGTERM. **Ask.** "After the interrupt, does the loop end?" **Fix.** Restore *and* return or propagate. **Seen in:** [PR04 F8](../03-Kafka-Beam-Dataflow-and-Distributed-Streaming-PR-Simulations/01-pr04-kafka-consumer-offset-commit-race-poison-pill-and-rebalance-storm.md).

#### J20 · `shutdownNow()` on in-flight work, or `close()` from another thread [grep]
**Smell.** `workers.shutdownNow(); consumer.close();` in a stop method. **Why.** Interrupts half-done side effects, and `KafkaConsumer` isn't thread-safe, so closing it from another thread races the poll loop. **Ask.** "What happens to the task running right now?" **Fix.** `wakeup()` the consumer, drain with `shutdown()` + `awaitTermination`, and close on the owning thread. **Seen in:** [PR04 F7](../03-Kafka-Beam-Dataflow-and-Distributed-Streaming-PR-Simulations/01-pr04-kafka-consumer-offset-commit-race-poison-pill-and-rebalance-storm.md).

#### J21 · Check-then-act on a cache (stampede) [judgment]
**Smell.** `if (entry == null || expired) { entry = fetch(); put(entry); }` with no single-flight. **Why.** At expiry every concurrent caller misses and calls the backend at once, so a hot key takes the dependency down. **Ask.** "What do 1,000 simultaneous misses do?" **Fix.** `computeIfAbsent`/single-flight per key, refresh-ahead, and jittered TTLs. **Seen in:** [PR03 F5](../02-Java-Spring-Hibernate-and-Microservices-PR-Simulations/03-pr03-multi-tenant-auth-cache-stampede-idor-and-jwt-security-flaws.md).

### D. Remote calls, time and locks

#### J22 · A timeout declared but never applied, or none at all [grep]
**Smell.** A `Duration …Timeout` property, while the call site has no `.timeout(...)`/client timeout. **Why.** A stalled dependency holds the request, thread and connection forever, and one stall per minute exhausts a pool by lunch. **Ask.** "Where is this timeout *used*?" **Fix.** Apply it at the call (`timeout`, client connect and read timeouts); test with a stalled stub. **Seen in:** [PR10 F8](../05-AI-Engineering-RAG-and-MCP-Server-PR-Simulations/01-pr10-spring-ai-rag-pipeline-sse-thread-starvation-and-acl-leakage.md).

#### J23 · `retry()` on a stream or a non-idempotent call [grep]
**Smell.** `.retry(2)` on a `Flux` of tokens, events or writes. **Why.** Re-subscribing replays what the consumer already received (duplicated text, double writes). In Spring AI 2.0.2 a `ChatClient` stream can't even be re-subscribed, so the retry only masks the real error. **Ask.** "What has the consumer already seen when this retries?" **Fix.** Retry only before the first element, around `Flux.defer` (a fresh request per attempt). **Seen in:** [PR10 F6](../05-AI-Engineering-RAG-and-MCP-Server-PR-Simulations/01-pr10-spring-ai-rag-pipeline-sse-thread-starvation-and-acl-leakage.md).

#### J24 · Blocking on a reactive stream [grep]
**Smell.** `toIterable()`, `block()`, `blockLast()` in request-serving code. **Why.** The calling thread is parked for the stream's whole life, so a fixed pool turns into a hard concurrency cap. **Ask.** "What thread waits here, and for how long?" **Fix.** Subscribe with callbacks, and `publishOn` a bounded scheduler only for blocking sinks. **Seen in:** [PR10 F1](../05-AI-Engineering-RAG-and-MCP-Server-PR-Simulations/01-pr10-spring-ai-rag-pipeline-sse-thread-starvation-and-acl-leakage.md).

#### J25 · The wall clock in event-time or business logic [grep]
**Smell.** `System.currentTimeMillis()` / `Instant.now()` as an event's timestamp, or in TTL arithmetic on the hot path. **Why.** Processing time isn't event time: replays and backfills land in the wrong windows, and clock steps break expiry. **Ask.** "Is this the time the event happened, or the time we noticed?" **Fix.** Reject or quarantine events without timestamps, use an injected `Clock`, and use monotonic time for durations. **Seen in:** [PR05 F7](../03-Kafka-Beam-Dataflow-and-Distributed-Streaming-PR-Simulations/02-pr05-apache-beam-stateful-dofn-watermark-stall-and-coder-non-determinism.md).

#### J26 · A publish or send whose result is ignored [grep]
**Smell.** `publisher.publish(...)` as a statement, returning a future nobody joins. **Why.** The cursor or offset advances before the broker acknowledges, so a rejected send is lost forever. **Ask.** "What if this send fails after we've moved on?" **Fix.** Join the futures (or collect and check them) before advancing; give events ids for consumer-side dedupe. **Seen in:** [PR06 F3](../03-Kafka-Beam-Dataflow-and-Distributed-Streaming-PR-Simulations/03-pr06-transactional-outbox-and-redis-distributed-lock-fencing-bugs.md).

#### J27 · A lease lock with no fencing [grep]
**Smell.** `setIfAbsent(key, owner, lease)` / `tryAcquire(...)`, then unguarded writes. **Why.** A GC pause or slow batch outlives the lease, a second holder starts, and both write. **Ask.** "What happens when the work outlasts the lease?" **Fix.** A fencing token checked by the resource, or `SKIP LOCKED` row claims instead of a global lock. **Seen in:** [PR06 F5](../03-Kafka-Beam-Dataflow-and-Distributed-Streaming-PR-Simulations/03-pr06-transactional-outbox-and-redis-distributed-lock-fencing-bugs.md).

#### J28 · A lock released without checking the owner [grep]
**Smell.** `redis.delete(key)` in `release()`. **Why.** After a lease expiry, the old holder deletes the *new* holder's lock, and a third instance enters. **Ask.** "Can this delete someone else's lock?" **Fix.** Compare-and-delete (`delete if value == owner`, atomically). **Seen in:** [PR06 F6](../03-Kafka-Beam-Dataflow-and-Distributed-Streaming-PR-Simulations/03-pr06-transactional-outbox-and-redis-distributed-lock-fencing-bugs.md).

### E. Kafka and Beam

#### J29 · An offset commit before processing [grep]
**Smell.** `commitAsync()` right after `poll()` and handing records to workers. **Why.** A crash after the commit loses every in-flight record (at-most-once by accident). **Ask.** "Is every record before this offset durably processed?" **Fix.** Commit per partition only up to the contiguous processed prefix. **Seen in:** [PR04 F1](../03-Kafka-Beam-Dataflow-and-Distributed-Streaming-PR-Simulations/01-pr04-kafka-consumer-offset-commit-race-poison-pill-and-rebalance-storm.md).

#### J30 · Auto-commit enabled or its "false" deleted [grep]
**Smell.** A removed `ENABLE_AUTO_COMMIT_CONFIG, "false"` line, or an added `"true"`. **Why.** With a `group.id` the effective default is `true`: offsets commit on a timer regardless of processing. **Ask.** "Who commits offsets now?" **Fix.** Keep it `false` explicitly, with commits owned by the processing path. **Seen in:** [PR04 F5](../03-Kafka-Beam-Dataflow-and-Distributed-Streaming-PR-Simulations/01-pr04-kafka-consumer-offset-commit-race-poison-pill-and-rebalance-storm.md).

#### J31 · `max.poll.records` raised with no backpressure [grep]
**Smell.** Bigger batches handed to an async pool with no `pause()`/`resume()`. **Why.** The consumer pulls the whole backlog into memory while workers fall behind: OOM on catch-up. **Ask.** "What bounds in-flight records?" **Fix.** A bounded in-flight count per partition, with pause/resume. **Seen in:** [PR04 F4](../03-Kafka-Beam-Dataflow-and-Distributed-Streaming-PR-Simulations/01-pr04-kafka-consumer-offset-commit-race-poison-pill-and-rebalance-storm.md).

#### J32 · `subscribe` without a rebalance listener [grep]
**Smell.** `consumer.subscribe(List.of(TOPIC))` with asynchronous processing. **Why.** On rebalance, revoked partitions' in-flight work keeps writing while the new owner reprocesses: duplicates and reordering. **Ask.** "What happens to in-flight work when a partition is revoked?" **Fix.** A `ConsumerRebalanceListener` that drains and commits on revoke. **Seen in:** [PR04 F6](../03-Kafka-Beam-Dataflow-and-Distributed-Streaming-PR-Simulations/01-pr04-kafka-consumer-offset-commit-race-poison-pill-and-rebalance-storm.md).

#### J33 · Id-cursor pagination over concurrently committed rows [grep]
**Smell.** `WHERE id > ? ORDER BY id` to tail a table that many transactions insert into. **Why.** Ids are assigned at insert and commit later, out of order. The cursor passes an id whose row commits afterwards, and it is skipped forever. **Ask.** "Can a smaller id commit after a larger one?" **Fix.** A `published_at IS NULL` flag with `FOR UPDATE SKIP LOCKED`, or a commit-ordered log (CDC). **Seen in:** [PR06 F2](../03-Kafka-Beam-Dataflow-and-Distributed-Streaming-PR-Simulations/03-pr06-transactional-outbox-and-redis-distributed-lock-fencing-bugs.md).

#### J34 · A custom Beam coder that claims determinism [grep]
**Smell.** `verifyDeterministic()` overridden to do nothing, on a coder for maps or sets. **Why.** Equal keys encode to different bytes, so grouping and state split one key into several. DirectRunner may not show it. **Ask.** "Is the encoding a function of the value, not the iteration order?" **Fix.** Sort before encoding, or use a deterministic standard coder. **Seen in:** [PR05 F1](../03-Kafka-Beam-Dataflow-and-Distributed-Streaming-PR-Simulations/02-pr05-apache-beam-stateful-dofn-watermark-stall-and-coder-non-determinism.md).

#### J35 · A map or content fingerprint used as the dedup key [grep]
**Smell.** `KV<Map<…>, …>` / "fingerprint" grouping for deduplication. **Why.** Distinct events with equal content merge. In fraud detection that hides card-testing bursts. **Ask.** "Can two different events have the same key?" **Fix.** Dedupe on the event's unique id. **Seen in:** [PR05 F2](../03-Kafka-Beam-Dataflow-and-Distributed-Streaming-PR-Simulations/02-pr05-apache-beam-stateful-dofn-watermark-stall-and-coder-non-determinism.md).

#### J36 · A timer output timestamp that holds the watermark [grep]
**Smell.** `timer.withOutputTimestamp(ts).set(ts.plus(24h))`. **Why.** The output watermark can't pass the hold, so every downstream window fires a day late. **Ask.** "What does this hold, and for how long?" **Fix.** No output timestamp for cleanup timers, or a hold at the window end. **Seen in:** [PR05 F3](../03-Kafka-Beam-Dataflow-and-Distributed-Streaming-PR-Simulations/02-pr05-apache-beam-stateful-dofn-watermark-stall-and-coder-non-determinism.md).

#### J37 · Window semantics changed: fixed for sliding, lateness removed [grep]
**Smell.** `FixedWindows.of(5m)` replacing sliding windows, or a deleted `withAllowedLateness(...)`. **Why.** Bursts across a boundary split under the threshold, and late data is dropped, which is sometimes masked until another bug is fixed. **Ask.** "Which real pattern does this window miss?" **Fix.** Keep the sliding windows for the semantics (or a stateful count per key), and keep explicit lateness. **Seen in:** [PR05 F4, F5](../03-Kafka-Beam-Dataflow-and-Distributed-Streaming-PR-Simulations/02-pr05-apache-beam-stateful-dofn-watermark-stall-and-coder-non-determinism.md).

#### J38 · A constant idempotency key, or events with no id [judgment]
**Smell.** `block(card, "velocity")`, a literal as the dedupe key, or payloads without an event id. **Why.** The receiver treats every later action as a replay (lost actions), or can't dedupe redeliveries (double actions). **Ask.** "What makes two *different* actions distinguishable, and one action recognizable when repeated?" **Fix.** A per-action id derived from the triggering event. **Seen in:** [PR05 F6](../03-Kafka-Beam-Dataflow-and-Distributed-Streaming-PR-Simulations/02-pr05-apache-beam-stateful-dofn-watermark-stall-and-coder-non-determinism.md), [PR06 F4](../03-Kafka-Beam-Dataflow-and-Distributed-Streaming-PR-Simulations/03-pr06-transactional-outbox-and-redis-distributed-lock-fencing-bugs.md).

### F. Security and tenancy

#### J39 · A JWT that chooses its own verification, or optional claims [grep]
**Smell.** Branching on the header's `"alg"`, or `if (exp != null && …)`, or no `aud`/`iss` check. **Why.** An `alg` the code doesn't handle skips the signature, a token without `exp` lives forever, and any audience's token works everywhere. **Ask.** "Which algorithm, issuer and audience does the *server* require?" **Fix.** Pin the algorithm and key, and require `exp`, `iss` and `aud` (RFC 8725). **Seen in:** [PR03 F1, F6, F7](../02-Java-Spring-Hibernate-and-Microservices-PR-Simulations/03-pr03-multi-tenant-auth-cache-stampede-idor-and-jwt-security-flaws.md).

#### J40 · Secrets compared with `equals` [grep]
**Smell.** `expected.equals(signature)`. **Why.** Early-exit comparison leaks how many leading bytes matched, a timing side channel (usually hard to exploit remotely, but a standard finding). **Ask.** "Is this compare on attacker-supplied secret material?" **Fix.** `MessageDigest.isEqual`. **Seen in:** [PR03 F8](../02-Java-Spring-Hibernate-and-Microservices-PR-Simulations/03-pr03-multi-tenant-auth-cache-stampede-idor-and-jwt-security-flaws.md).

#### J41 · Tenant or identity taken from the request [grep]
**Smell.** `String tenant = tenantHeader;`, `X-Tenant-Id`, or a user id in the body. **Why.** The caller chooses whose data to read: cross-tenant IDOR. **Ask.** "Where does this value come from, and is it authenticated?" **Fix.** Derive it from the verified token or session only. **Seen in:** [PR03 F2](../02-Java-Spring-Hibernate-and-Microservices-PR-Simulations/03-pr03-multi-tenant-auth-cache-stampede-idor-and-jwt-security-flaws.md).

#### J42 · A cache key missing part of the scope [grep]
**Smell.** `cache.get(userId)` in a multi-tenant service, or `cache.lookup(request.question())`. **Why.** One tenant's or group's result is served to another, which is a disclosure with no query involved. **Ask.** "Which inputs decided this value, and are all of them in the key?" **Fix.** Key = tenant + principal scope + every filter. **Seen in:** [PR03 F3](../02-Java-Spring-Hibernate-and-Microservices-PR-Simulations/03-pr03-multi-tenant-auth-cache-stampede-idor-and-jwt-security-flaws.md), [PR10 F4](../05-AI-Engineering-RAG-and-MCP-Server-PR-Simulations/01-pr10-spring-ai-rag-pipeline-sse-thread-starvation-and-acl-leakage.md).

#### J43 · Broad catch blocks that fail open or silent [grep]
**Smell.** `catch (RuntimeException e) { return FALLBACK; }` in an authorization or validation path. **Why.** During an outage everyone gets the fallback permissions. Elsewhere, errors disappear. **Ask.** "What does the caller get when the dependency is down?" **Fix.** Fail closed for security decisions; narrow catches; serve stale data only with explicit, scoped intent. **Seen in:** [PR03 F4](../02-Java-Spring-Hibernate-and-Microservices-PR-Simulations/03-pr03-multi-tenant-auth-cache-stampede-idor-and-jwt-security-flaws.md).

#### J44 · Query or filter text built by concatenation [grep]
**Smell.** `"… dept == '" + department + "'"`, SQL/JPQL/filter strings with `+`. **Why.** Quotes in the value become syntax. In PR10 one dropdown value rewrites a tenant-scoped vector search into a global one. **Ask.** "Can this value contain the language's quote or operator characters?" **Fix.** Bind parameters, builder APIs (`FilterExpressionBuilder`), and allow-lists. **Seen in:** [PR10 F7](../05-AI-Engineering-RAG-and-MCP-Server-PR-Simulations/01-pr10-spring-ai-rag-pipeline-sse-thread-starvation-and-acl-leakage.md).

### G. AI serving and agent tools

#### J45 · Paths or URLs from model or user input without containment [grep]
**Smell.** `base.resolve(path)` with no `normalize`/`startsWith`, or `URI.create(url)` straight into a fetcher. **Why.** `../secrets` reads files, and `http://169.254.169.254/…` returns cloud credentials into the model's context. **Ask.** "What is the set of reachable files and hosts?" **Fix.** `normalize` + `startsWith` + `toRealPath`; an https host allow-list, no redirects, an egress proxy. **Seen in:** [PR11 F4, F5](../05-AI-Engineering-RAG-and-MCP-Server-PR-Simulations/02-pr11-mcp-tool-server-confused-deputy-and-non-idempotent-agent-retries.md).

#### J46 · Exception text returned to callers or models [grep]
**Smell.** `return text("error: " + e.getMessage())`. **Why.** Downstream messages carry hosts, keys and personal data, and without `isError: true` the agent treats the failure as success. **Ask.** "What can this message contain, and does the client know it failed?" **Fix.** `isError: true`, safe validation text, and a reference id with details logged server-side. **Seen in:** [PR11 F6](../05-AI-Engineering-RAG-and-MCP-Server-PR-Simulations/02-pr11-mcp-tool-server-confused-deputy-and-non-idempotent-agent-retries.md).

#### J47 · Access control applied after retrieval, or to citations only [judgment]
**Smell.** `visible = docs.filter(acl)` for display while the prompt uses `docs`. **Why.** Anything in the context window can appear in the answer, so the filtered citations hide a disclosure. **Ask.** "Which list does the model read?" **Fix.** Enforce tenant and ACL in the retrieval filter, with one list for context and citations. **Seen in:** [PR10 F3](../05-AI-Engineering-RAG-and-MCP-Server-PR-Simulations/01-pr10-spring-ai-rag-pipeline-sse-thread-starvation-and-acl-leakage.md).

#### J48 · Token passthrough, or a privileged credential used without checking the caller [grep]
**Smell.** `orders.lookup(caller.bearerToken(), …)`, or `payments.refund(serviceCredential, …)` with no role check. **Why.** Forwarding a token outside its audience breaks trust boundaries (an MCP MUST NOT). Using the server's own authority for any caller makes the server a confused deputy. **Ask.** "Whose authority does this call exercise, and who checked it?" **Fix.** The server's credential plus `onBehalfOf`, the caller's limits enforced first, or token exchange. **Seen in:** [PR11 F1, F2](../05-AI-Engineering-RAG-and-MCP-Server-PR-Simulations/02-pr11-mcp-tool-server-confused-deputy-and-non-idempotent-agent-retries.md).

#### J49 · Side-effecting tools with no idempotency key, or with wrong annotations [grep]
**Smell.** `refund(..., null, null)` (no key), `.annotations(READ_ONLY)` on a money-moving tool. **Why.** Agents time out and retry, so money moves twice, and read-only hints let clients skip the human confirmation. **Ask.** "What does the second identical call do, and will the client ask a human?" **Fix.** A required `idempotency_key` executed once per (caller, key); `destructiveHint = true`. **Seen in:** [PR11 F3, F8](../05-AI-Engineering-RAG-and-MCP-Server-PR-Simulations/02-pr11-mcp-tool-server-confused-deputy-and-non-idempotent-agent-retries.md).

#### J50 · `finally` doing completion-only work [grep]
**Smell.** `cache.put(...)`, offset commits or "success" metrics in `finally`. **Why.** `finally` runs on cancel, error and timeout too, so partial answers get cached and failures get counted as successes. **Ask.** "Which terminal states should do this?" **Fix.** Do it on success (`onComplete`, after the try body), and clean up only in `finally`. **Seen in:** [PR10 F5](../05-AI-Engineering-RAG-and-MCP-Server-PR-Simulations/01-pr10-spring-ai-rag-pipeline-sse-thread-starvation-and-acl-leakage.md).

### Beyond the 50: the deleted test

`T01` (scanner rule, both languages) fires on any removed `@Test`, test method, `TEST(` or C test function. It fires in 9 of this KB's 11 PRs, because most PRs rewrite their suites. In five of them, the deleted test is exactly the one that would have caught a planted defect: PR07 `corrupt_input_throws` (F3), PR08 `feed_handler_counts_drops` (F8), PR09 `drops_duplicate_sequence` (F1), PR10 `restrictedDocumentsNeverReachTheAnswer` (F3) and PR11 `refusesPathsOutsideTheRunbookDirectory` (F4). A deleted test is cheap to spot and expensive to ignore: open the old version and ask what it asserted.

### 3.2 How to read the numbers

| Observation | Number | Lesson |
|---|---|---|
| Defects flagged on their own line | 51 / 61 | Optimistic by construction: these rules and these PRs were written together |
| Coincidental hits | e.g. PR03 F5 by J25 | A rule can fire on the right line for the wrong reason; the reviewer still has to name the actual bug |
| Judgment-only | 10 / 61 | Missing things (an `aud` check, a currency compare), ordering (idempotency last, outbox outside the transaction) and unchanged lines are invisible to grep |
| False alarms on changed lines | 28 | Examples: `Instant.now()` used only for a timestamp column, `join fetch` that is correctly paginated (PR02 D1), `finally` that only cleans up |
| Flags on corrected code | 63 | Fixed code still publishes events (J26 ×6), parses amounts (J07 ×6), maps exceptions to tool errors (J43 ×5), cleans up in `finally` (J50 ×5), uses the service credential after authorizing the caller (J48 ×5) and takes `FOR UPDATE` locks in order (J03 ×4), all correctly. A scanner can't tell PR11's fixed refund from its broken one |

**How to use a scanner in the round.** Run your mental version of it at minute 2, write the questions, then *spend your time on the judgment flags*: they're where L7 candidates separate from L5s, because no tool finds them.

## 4. Failure modes (using red-flag lists)

| Failure mode | What it looks like | Why it fails |
|---|---|---|
| Treating flags as findings | "Line 42 uses `synchronized`, blocking" | Many hits are correct code (63 on the fixed PRs); a comment without a mechanism fails the rubric |
| Stopping at the list | Ten flags written, no judgment pass | The judgment-only defects (remote call in a transaction, missing `aud`) are the Sev-1s grep can't see |
| Reviewing only changed lines | Misses PR11 F8, PR08 F7 | The defect's other half is an unchanged line one screen away |
| No ranking | Fifteen comments, equal weight | Interviewers grade prioritization; lead with blast radius |
| Pattern without consequence | "N+1 here" | Needs "100 orders make 101 queries; p99 scales with page size; join fetch fixes it" |
| Ignoring deleted tests | Reviews new tests only | In five PRs here, the deleted test was the one that would have caught a defect |

## 5. Bar-raiser chains

<details><summary><b>Q1 · "You flagged `synchronized`. Is it a bug?"</b></summary>

**Initial Prompt.** Flag versus finding.

**L5 Answer.** "Yes, synchronized hurts performance."

**Why L5 Stalls.** A blanket claim, and often wrong. Uncontended locks are cheap.

**L7 Answer.** "It depends on what's inside and who's calling. Here the block wraps a remote refresh: every caller waits behind one HTTP call, and on JDK 21–23 virtual threads pin their carrier while blocked inside `synchronized` (JEP 491 removed that in 24). So it's a bug *because* of the remote call, and I'd move the refresh outside the lock with single-flight. Around a counter increment I'd leave it alone."

</details>

<details><summary><b>Q2 · "A tool flags 40 lines in this PR. How do you triage?"</b></summary>

**Initial Prompt.** Working with scanner output.

**L5 Answer.** "Go through them in order."

**Why L5 Stalls.** Linear triage spends the time budget on false alarms.

**L7 Answer.** "Group by mechanism, then ask one context question per group. Do security flags first, because they're cheap to confirm and expensive to miss; lifecycle flags next (transactions, streams, leases), which carry the outage risk; style-adjacent ones last. On this KB the scanner's noise is about one false alarm per two real defects, and it still flags corrected code, so each flag gets a ten-second 'is the mechanism present?' check before it earns a comment. Then I spend most of the time on what no tool flags."

</details>

<details><summary><b>Q3 · "Which red flags can't be grepped, and how do you find them?"</b></summary>

**Initial Prompt.** The judgment layer.

**L5 Answer.** "You read carefully."

**Why L5 Stalls.** True, but not a method.

**L7 Answer.** "They're absences and orderings. Absences: no `aud` check, no currency compare, no timeout applied. Orderings: idempotency claimed after side effects, outbox outside the transaction, ACL applied after retrieval. Context: an unchanged capacity constant, shared annotations. I find them with three questions per hunk: what must be true before this line (preconditions), what happens if this runs twice (idempotency), and which unchanged line completes this behavior."

</details>

<details><summary><b>Q4 · "Why is a deleted test a red flag if the PR adds more tests?"</b></summary>

**Initial Prompt.** Test-suite changes as evidence.

**L5 Answer.** "Coverage might drop."

**Why L5 Stalls.** Coverage isn't the point. Deleted *assertions* are.

**L7 Answer.** "A deleted test is a deleted specification. In this KB, five PRs deleted exactly the test that would have caught one of their defects. PR11 removed `refusesPathsOutsideTheRunbookDirectory` in the same diff that dropped the path check. I open the old test, read what it asserted, and ask whether the new code still guarantees it. If it doesn't, that's usually the most important comment in the review."

</details>

<details><summary><b>Q5 · "How would you turn this list into CI checks?"</b></summary>

**Initial Prompt.** Automation strategy.

**L5 Answer.** "Add the regexes to a linter."

**Why L5 Stalls.** Regexes alone produce noise that teams learn to ignore.

**L7 Answer.** "Tier them. Hard failures, where the pattern is almost never right: string-built queries and filters, `@EventListener` on transactional events in this codebase, tool handlers reading the raw `authorization` header, deleted `@Test` without a linked replacement. Use semantic tools where they exist: ArchUnit for 'no HTTP client calls inside `@Transactional` services', Error Prone for interrupt handling, Spring's own warnings for open-in-view. Everything else becomes a *review prompt* bot that posts the question, not a block. Measure noise and retire rules that people dismiss."

</details>

<details><summary><b>Q6 · "J42 and J47 are both about scope. Why separate flags?"</b></summary>

**Initial Prompt.** Precision in security reasoning.

**L5 Answer.** "They're the same issue."

**Why L5 Stalls.** Same family, different mechanism and fix location.

**L7 Answer.** "J42 is reuse across scopes: a cache serving one scope's result to another, fixed in the key. J47 is exposure within a request: the model reads documents the user may not, fixed in the retrieval filter. PR10 has both, and fixing one leaves the other: a scoped cache still caches answers that quote restricted documents if retrieval isn't filtered. Naming them separately makes sure both get fixed."

</details>

<details><summary><b>Q7 · "Is `Instant.now()` ever a red flag in a CRUD service?"</b></summary>

**Initial Prompt.** Context sensitivity.

**L5 Answer.** "No, that's fine."

**Why L5 Stalls.** Usually fine, but not always.

**L7 Answer.** "For a `created_at` column it's fine. It's a flag when it stands in for *event* time (a replayed event gets today's timestamp, as in PR05 F7), when it's compared with deadlines across services with skewed clocks, or when it makes tests nondeterministic. The fix varies: an event timestamp from the source, monotonic time for durations, an injected `Clock` for testability. The flag is the prompt to ask which of those it is."

</details>

<details><summary><b>Q8 · "Pick the five flags you'd teach a new reviewer first."</b></summary>

**Initial Prompt.** Prioritizing the list itself.

**L5 Answer.** "The security ones."

**Why L5 Stalls.** Partially right; misses the most common production outages.

**L7 Answer.** "J04 (remote call inside a transaction), because it's the most common pool-exhaustion outage. J29 (commit before processing), the classic silent data loss. J41/J42 (scope from the request, or missing from cache keys), the multi-tenant disclosures. J23/J49 (retries on non-idempotent work), duplicates in money flows. And T01, the deleted test. Together they cover the outage, loss, disclosure and duplication classes, and each comes with a one-question test a new reviewer can apply."

</details>
