# How Companies Grade Live PR Review Rounds: L5 vs L6 vs L7

> **What this file is.** The scoring model behind the "live pull-request review / bug-hunt" interview round, taken apart until you can grade yourself. It has an eight-dimension rubric with level anchors and a severity-weighted scoring method. It also includes a 45-minute game plan and one fully worked exhibit, **PR-00**: a real, compiling, test-passing Java 21 diff with nine planted defects, graded across three candidate transcripts (L5, L6, L7). ## 0. Orientation

### 0.1 What the round is

The round goes by different names: "code review," "PR review," "bug squash," "bug bash," "debugging," "code reading." Underneath, it is one exercise: **you are handed code you did not write and asked to find what will hurt production, then say so in a way the author can act on.** Four formats show up in public candidate reports and company prep material:

| Format | Shape | What it stresses |
|---|---|---|
| **Diff review** | A 100–300 line PR in a GitHub-like UI, CoderPad or a shared IDE. Leave comments for 40–60 min, then talk them through. | Prioritization, communication, production judgment |
| **Bug squash / debugging** | An unfamiliar repo with failing tests; find the root cause and fix it. Stripe's "Bug Squash" round is the best-known public example (candidate reports on Glassdoor and 1Point3Acres describe a repo with failing tests, run locally). | Navigation speed, root-causing, hypothesis discipline |
| **Read-and-extend** | "Here is our service. Review it, then add feature X." | Model-building, spotting latent bugs before you build on them |
| **Take-home review + live defense** | Review asynchronously, then defend your comments while the interviewer plays the author pushing back. | Calibration, handling disagreement, mentoring tone |

⚠ Which companies run which format changes by team and year. The six companies the brief names (Meta, Stripe, Uber, Apple, Confluent, NVIDIA) are used in §8 as *domain lenses*: what interviewers from those domains tend to probe, inferred from their public engineering material and products. Treat them as lenses, not as claims about any loop.

### 0.2 Why companies run it at L6/L7

An algorithm round shows you can write correct code under time pressure. It cannot show the three things that make a Staff+ engineer's review worth more than an L5's:

1. **Reading at the speed of risk.** Production code is read far more often than it is written, and a Principal's leverage is mostly in *other people's* diffs. The round tests whether you can build a working model of unfamiliar code fast enough to find the line that pages someone at 3 a.m.
2. **Judgment about severity.** Every PR has twenty things you *could* say. The round tests whether you can tell a Sev-1 from a nit and spend your time accordingly.
3. **Changing the author's mind without damage.** A correct comment that the author ignores, or resents, protects nothing. The round tests whether your feedback produces the fix *and* a better engineer.

### 0.3 Habits that cap you at L5, and what replaces them

| Habit | What the interviewer sees | L7 replacement |
|---|---|---|
| Read the diff top to bottom | No prioritization; Sev-1s found late or never | Read the ticket and the file list first, then go straight to the riskiest hunk (state mutation, external call, contract change, trust boundary) |
| Count bugs | Volume over judgment | Rank by blast radius; say why #1 is #1 |
| Comment on naming and formatting early | Bikeshedding; time spent where linters already work | "I'll batch style at the end; first I'm looking for anything that loses money or data" |
| "This looks wrong" | A verdict with no mechanism | "Pod A and pod B both read `refunded = 0`, both pass the check, the network pays 12,000 on a 10,000 charge. Here's the interleaving" |
| Rewrite it your way | Ego; unreviewable counter-proposal | The smallest change that makes it safe, plus a follow-up for the redesign, with a migration path |
| Treat green tests as evidence | Trusts the author's model of the system | Ask what the tests *can't* see: two pods, timeouts, failover, old consumers, other tenants |
| Stop at the first bug in a function | Tunnel vision | Note it, keep sweeping, come back to prove it |
| Go silent while thinking | Interviewer can't award what they can't hear | Narrate the model: "I'm checking what happens if this call times out after the money moved" |

## 1. First principles: what the round actually measures

### 1.1 The interviewer has an answer key; you are graded on the path

Unlike system design, a PR review round has a **known, fixed defect set**. The interviewer (or the question's author) planted or curated every bug, knows which ones a strong candidate finds in 45 minutes, and usually has a tiered key: surface bugs, one-hop bugs, and model-dependent bugs. Two consequences follow:

- **Recall is necessary, not sufficient.** Two candidates who find the same six bugs can get opposite decisions. One found the Sev-1s first, proved each with a concrete interleaving and proposed a coherent fix. The other found the nits first, stumbled onto the Sev-1s at minute 35 and proposed patches that reintroduced the defect elsewhere. The interviewer writes down *how* you found each bug.
- **False positives cost real credibility.** Confidently asserting a bug that isn't one ("this `ConcurrentHashMap` read is a data race") tells the interviewer your *true* positives might be guesses too. A hedged hypothesis with a plan to check ("I think this might race; let me trace who else writes `refunded_minor`") costs nothing.

### 1.2 Reviews are mostly about understanding, and the round knows it

The empirical literature on industrial code review agrees on one finding. Bacchelli and Bird's Microsoft study found that "while finding defects remains the main motivation for review, reviews are less about defects than expected." Reviews also bring knowledge transfer and team awareness, and the study names "code and change understanding" as "the key aspect of code reviewing." Google's public reviewer guide makes the reviewer's job explicit: approve a change "once it is in a state where it definitely improves the overall code health … even if the CL isn't perfect."

For the interview this means:

- **Your first five minutes are model-building, not bug-hunting.** What does this PR change about the system's contract? Who calls it now that didn't before? What state does it mutate, and what external systems does it touch?
- **The bar is "safe and better," not "perfect."** A candidate who blocks the PR on twenty items reads as someone teams route around. A candidate who blocks on four, explains each, and files the rest as follow-ups reads as someone teams seek out.

### 1.3 Time pressure is about prioritization, not reading speed

SmartBear's study of a Cisco programming team is the most-cited source on review effectiveness. It recommends reviewing "no more than 200 to 400 lines of code (LOC) at a time." It reports a "significant drop in defect density at rates faster than 500 LOC per hour," and advises against reviewing for more than 60 minutes at a time. A 150-line diff in 45 minutes is about 200 LOC/hour, comfortably inside the effective range. **So the round is not a speed-reading test.** You have time to read every line. You do not have time to *reason deeply* about every line, so the skill being measured is choosing which lines get the deep reasoning.

### 1.4 The three questions behind every hire/no-hire

Strip away the rubric and an interviewer's write-up answers three questions:

1. **Impact:** did they find what would have hurt us, in the order it would have hurt us?
2. **Rigor:** did they *prove* it, with a mechanism, an interleaving, a failing input or a probe, rather than pattern-matching?
3. **Trust:** would I want this person reviewing my team's code tomorrow, alone, with the author in a different time zone?

Every row of the rubric in §2 is a finer-grained version of one of these three.

### 1.5 What changes from L5 to L7

The defect set does not change with level. The *unit of analysis* does:

| Level | Unit of analysis | Typical sentence |
|---|---|---|
| L5 Senior | The **line** | "Line 40 can overflow." |
| L6 Staff | The **system the line runs in** | "Line 40 overflows for IDR charges, and because the method is only synchronized per JVM, two pods can both pass the balance check anyway." |
| L7 Principal | The **change as an event in the system's life**: its contracts, its rollout, its failure modes, and the class of bug it belongs to | "This PR turns an internal, single-instance admin path into a public multi-pod API. The JVM lock, the trust in `chargeId` and the renamed event field were all safe under the old contract and are all Sev-1 under the new one. Here's the design that makes the database the source of truth, the two blockers to fix before merge, and the CI check that stops the next rename." |

## 2. The eight-dimension rubric (composite) ⚠

No company publishes its live-review rubric. The eight dimensions below are a composite that covers what interviewer write-ups consistently comment on. The weights are a teaching device: they reflect how strongly each dimension separates levels in practice, not a published formula.

| # | Dimension | What the interviewer observes | Teaching weight |
|---|---|---|---|
| D1 | **Severity triage** | Sev-1s found first; explicit ranking; time-to-first-Sev-1 | 20 |
| D2 | **Root-cause depth** | Explains the *mechanism* (interleaving, overflow arithmetic, ordering, contract) rather than the symptom | 15 |
| D3 | **Evidence** | Concrete failing input, interleaving, probe or test; distinguishes "proven" from "suspected" | 10 |
| D4 | **Fix quality** | Minimal, correct, testable; doesn't move the bug elsewhere; names the test that pins it | 15 |
| D5 | **Production reasoning** | Blast radius, detection, rollout, rollback, reconciliation, what the dashboards would show | 15 |
| D6 | **Communication** | Labeled severity, actionable, kind, author-centric; narrates while thinking | 10 |
| D7 | **Coverage and time** | Systematic sweep (all 7 layers), no tunnel vision, lands a summary on time | 5 |
| D8 | **Leverage beyond the diff** | Tests, guardrails, lint/CI rules, design follow-ups, mentoring the author on the bug *class* | 10 |

Two notes on using it:

- **D1 and D4 together are the main level separators.** L5 candidates often find Sev-1s but late. L6 candidates find them early but sometimes "fix" them by moving the defect, for example swapping a JVM lock for a database row lock held across the same network call. L7 candidates find them early *and* propose a design in which the whole class of defect cannot occur.
- **D6 is rarely the reason for a hire, and often the reason for a no-hire.** A brilliant review delivered as "why would you do this?!" fails the trust question in §1.4. File [03](03-high-leverage-communication-mentoring-tone-vs-blocking-nitpicks.md) is entirely about D6.

## 3. Level anchors: L5 vs L6 vs L7 per dimension

| Dimension | L5 Senior (meets bar for L5) | L6 Staff | L7 Principal / Senior Staff |
|---|---|---|---|
| **D1 Severity triage** | Finds real bugs but in reading order; first Sev-1 after ~20 min; ranks only when asked | Goes to state mutations and external calls first; first Sev-1 in ~10 min; ranks unprompted | Reads the ticket for *contract changes* first; first Sev-1 in ≤ 5 min; ranks by blast radius × likelihood × reversibility and says why |
| **D2 Root-cause depth** | Names the pattern ("race condition," "overflow") | Gives the mechanism for one process (thread interleaving, exact overflow value) | Gives the mechanism across processes, versions and time (two pods, a v1 consumer, a timeout after commit), and names the violated invariant |
| **D3 Evidence** | "This could break" | One concrete scenario per Sev-1 | A scenario per Sev-1 plus the test or probe that would fail today and pass after the fix; flags which claims are unverified |
| **D4 Fix quality** | Local patch (`int` → `long`; add `synchronized`) | Correct local fix but sometimes moves the defect (row lock across I/O) | A coherent design: source of truth, idempotency, state machine, outbox, with the *minimal* merge-blocking subset separated from follow-ups |
| **D5 Production reasoning** | Rarely mentions deployment | Mentions replicas, retries, timeouts | Covers rollout (flag, canary), detection (which alarm fires), reconciliation (how money/data is repaired) and rollback safety (can v1 read v2's writes?) |
| **D6 Communication** | Correct but unlabeled; some "you should"; nits mixed with blockers | Labeled, clear, mostly kind | Labeled, kind, short; one summary comment with verdict, blockers and follow-ups; teaches the bug class; offers to pair |
| **D7 Coverage and time** | Deep on one area, misses whole layers (compat, security) | Covers most layers; may run out of time before summary | Sweeps all seven layers, time-boxes deliberately, lands the summary with minutes to spare |
| **D8 Leverage** | Asks for a unit test | Asks for the specific concurrency/failure test | Asks for the test *and* the guardrail: schema-compat check in CI, ArchUnit/Error Prone rule, metrics-label allowlist, a design doc for the refund state machine |

> **The downlevel pattern.** The most common outcome for a strong-but-not-L7 candidate is not "no hire" but **"hire at L6."** The tell is almost always D4 + D5: they found the bugs and fixed them one at a time, but never stepped back to say "these five bugs are one bug: the PR moved the source of truth from the database into the JVM."

## 4. Scoring mechanics ⚠

### 4.1 The answer key has tiers

Question authors classify each planted defect twice: by **severity** and by **findability**.

| Severity | Definition (production) | Teaching weight |
|---|---|---|
| **Sev-1** | Loses or corrupts money or data, breaches security, or breaks a deployed consumer, at realistic volume, possibly silently | 5 |
| **Sev-2** | Outage, severe degradation, or corruption that needs an unlikely-but-real trigger (failover mid-request, gateway brownout) | 3 |
| **Sev-3** | Cost, observability or maintainability damage that compounds (metric cardinality, missing timeouts on a non-critical path) | 1 |
| **Nit** | Style, naming, comment wording | 0 |

| Findability tier | What it takes | Typical examples |
|---|---|---|
| **Minute-2** | Visible on the line itself to anyone looking for the pattern | Unchecked `int` addition on money, `catch (TimeoutException \| DeclinedException)` lumped together, a field renamed on a `v1` topic |
| **Minute-10** | One hop: read a caller, a contract, or the ticket | The `merchantId` parameter is documented as authenticated but never compared; the endpoint became public in this PR |
| **Minute-20** | A model of concurrency, distribution or time | `synchronized` is per-JVM and the service runs six pods; the record is saved only *after* the gateway call, so a crash in between leaves no trace |

A good question has Sev-1s in all three tiers. A Sev-1 in the Minute-20 tier is what separates L6 from L7.

### 4.2 Severity-weighted recall, precision, and order

The interviewer's notes reduce, informally, to three numbers. The formalization below is a composite ⚠:

- **Weighted recall** = Σ weights of defects found ÷ Σ weights of the key. A defect counts as "found" only with its mechanism. "Something feels off about the timeout handling" is a half-credit hint at best.
- **Precision**: each confidently asserted false positive costs about one Sev-3 of credit, and a confidently asserted *false Sev-1* costs much more, because it makes the interviewer discount everything else you said. A hedged hypothesis ("I'd want to check whether the gateway dedupes by key") costs nothing.
- **Order**: time-to-first-Sev-1, and whether the final summary ranks blockers correctly.

On top of these, D4–D8 are judged qualitatively: fix quality, production reasoning, communication, leverage.

### 4.3 Calibration language that earns credit

| Instead of | Say | Why it scores |
|---|---|---|
| "This is a race condition." | "I'm fairly confident two pods can both pass this check. Here's the interleaving. Can you confirm we run more than one replica?" | States confidence, gives the mechanism, asks the one fact that decides it |
| "This might overflow." | "`int` addition at line 40: 1.5 B already refunded + a 1 B request wraps to −1,794,967,296, which is less than the 2 B charge, so the check passes." | Turns "might" into a number |
| "Tests look fine." | "The tests are all single-threaded, single-instance, and the gateway never times out after committing. None of them can see bugs 3, 4 or 6." | Shows you understand what tests *cannot* prove |
| "I'd rewrite this." | "Minimum to merge: claim the key and reserve the balance in the DB before the call. Follow-up: the outbox and the reconciler, which I'd scope in a short design doc." | Separates blocking from aspirational |

### 4.4 The decision

| Outcome | Typical evidence pattern |
|---|---|
| **Strong No Hire** | False Sev-1s asserted confidently; dismissive tone; argues with the interviewer-as-author |
| **No Hire** | Found mostly nits; Sev-1s missed or found without mechanism; no summary |
| **Lean Hire (at level)** | Found most Sev-1s with mechanism but late; local fixes; communication fine |
| **Hire (at level)** | Sev-1s early, proven, ranked; fixes correct; clear summary |
| **Strong Hire (at level)** | All of the above plus a design-level fix, rollout/reconciliation plan, guardrails, and a review the author would thank them for |

The level decision is separate from the hire decision. The same transcript can be a "Strong Hire at L5" and a "No Hire at L7". The three transcripts in §6 show exactly how.

## 5. The PR-00 exhibit

PR-00 is deliberately small (158 diff lines), so you can hold all of it in your head while learning the grading. The PR simulations in Folders 02–05 follow the same format at 100–150 lines with 7–10 defects each.

### 5.1 The ticket and the PR description (as the author wrote them)

> **PAY-4127 · Partial refunds for the public Refunds API**
>
> Merchants have asked for partial refunds. Today the support console can only issue full refunds, through `RefundService.refundFull`, which only staff agents call. This ticket exposes refunds on the public API (`POST /v1/refunds`, authenticated by merchant API key) and supports any amount up to the remaining balance.
>
> **PR description, by the author:**
> - Replaces `refundFull(chargeId, key)` with `refund(merchantId, RefundRequest)` supporting partial amounts.
> - Idempotent: requests are de-duplicated by `Idempotency-Key`, so clients can retry safely.
> - Thread-safe: the method stays `synchronized`, so two concurrent partial refunds can't both pass the balance check.
> - Renames the event field `amountCents` → `amountMinor`, because "cents" is wrong for JPY (0 decimals) and KWD (3 decimals).
> - Adds `refunds.failed` / `refunds.succeeded` counters.
> - All tests pass (6 tests, up from 2).

## 7. The 45-minute game plan

### 7.1 Timeline

| Minutes | Goal | What you do | What you say aloud |
|---|---|---|---|
| **0–2** | Orient | Read the ticket/PR description, file list, diff size. Identify contract changes: callers, deployment shape, retries, consumers, data shape | "This PR changes X for callers Y. I'll check those boundaries first. Quick questions: replicas? Retry semantics? Who consumes this event?" |
| **2–10** | Sev-1 radar | Go straight to the riskiest hunks: trust boundary checks, money/state mutation, every external call, every serialized format change. One line per suspicion in a scratch list | "Suspicion: the lock is held across the gateway call. I'll come back and prove it." |
| **10–20** | Deep pass | For each external call: what if it times out, fails, succeeds-then-crashes? For each shared state: what if two instances run this? For each format: what does the deployed old reader do? | Concrete interleavings and numbers |
| **20–32** | Prove and fix | Turn suspicions into findings with mechanisms; propose fixes; look for the common root cause | "Five of these share one cause; here's the design-level fix" |
| **32–40** | Sweep | Layers you haven't touched (operability, perf, tests, docs); batch nits | "Nits batched into one non-blocking comment" |
| **40–45** | Land it | Summary: verdict, ranked blockers, follow-ups, praise, offer | The summary comment (03 §10) |

### 7.2 Clarifying questions that earn credit

Ask few, decisive ones. Each should change your answer:

1. **"How many instances run this, and is there any sticky routing?"** Decides every in-process lock.
2. **"What are the dependency's semantics on timeout and retry? Does it dedupe?"** Decides idempotency and the meaning of an error.
3. **"Who reads this data or event today, and which versions are deployed?"** Decides compatibility.
4. **"Who can call this endpoint, and what identity reaches this method?"** Decides authorization.
5. **"What's the expected volume and the largest realistic value?"** Decides overflow, cardinality, N+1.

Questions that *cost* credit: anything answered by the diff itself; style-guide questions; "what does this method do?" when it is ten lines long.

### 7.3 The scratch list

Keep a running list in a comment box or notepad: `F? L4 lock across gateway call (31,46) — prove`. It makes your coverage visible, protects you from losing a suspicion while chasing another, and *is* your summary at minute 40.

## 9. Red flags interviewers write down

| Red flag | Why it hurts | Do instead |
|---|---|---|
| First 10 minutes on naming and formatting | Signals you can't tell severity | Say "batching style for the end" and go hunting |
| "This is wrong" without a mechanism | Unfalsifiable; reads as guessing | Give the input, interleaving or contract that breaks it |
| Asserting a false Sev-1 confidently | Discounts all your true positives | Hedge and say how you'd check |
| Rewriting the whole PR in comments | Unreviewable; ignores the author's constraints | Minimal blocking fix + follow-up ticket |
| Trusting green tests | Tests only cover what the author imagined | Name the scenarios tests can't see |
| Fixing a lock bug with a bigger lock across the same I/O | Moves the defect, often to shared infrastructure | Shrink the critical section; use conditional writes |

## 10. Failure modes (of candidates, not code)

| Failure mode | Symptom in the round | Root cause | Fix in your prep |
|---|---|---|---|
| **Reading-order review** | Sev-1s found in the order they appear in the file | No triage model | Drill the Minute-2 radar (02 §2) on every PR in Folders 02–05 |

## 11. Bar-raiser chains

<details><summary><b>Q1 · "You found eight issues. The release train leaves in an hour and the author can fix two. Which two, and what happens to the rest?"</b></summary>

**Initial Prompt.** Forced prioritization under a hard constraint.

**L5 Answer.** "The overflow and the synchronized one, because those are the bugs in the core logic."

**Why L5 Stalls.** Prioritizes by where the bug is, not by blast radius × likelihood × detectability × reversibility. Misses that one of the cheapest fixes (restoring `amountCents`) prevents silent corruption on deploy, and that the authz hole is exploitable by anyone with an account.

**L7 Answer.** "Neither fix should ride this train. The honest answer is to pull PAY-4127 from it. But if I must pick two one-hour fixes that make shipping *least* dangerous: (1) the ownership check, a one-line change to `findForMerchant`, because F1 is exploitable on day one by any merchant; (2) restoring `amountCents` on v1, also one line, because F8 silently corrupts the ledger from the first refund. Everything else needs the source-of-truth refactor, so I'd keep the feature flag off for all merchants until it lands. Then F3/F4/F6/F7 can't fire, because the old console path is single-instance. I'd write that decision into the PR so it's explicit, with tickets for the refactor and owners."

</details>

<details><summary><b>Q2 · "Prove the cross-pod over-refund to me without running anything."</b></summary>

**Initial Prompt.** Evidence without tools: can the candidate construct an interleaving?

**L5 Answer.** "Two threads could enter at the same time and both pass the check."

**Why L5 Stalls.** "Two threads" is wrong for this code: within one pod, `synchronized` does serialize them. The bug needs two *pods*. A vague race claim invites "but it's synchronized" and the candidate has no reply.

**L7 Answer.** "Charge 10,000, refunded 0, six pods. t0: pod A enters its monitor and reads `refunded = 0`. t1: pod B, a different JVM and a different monitor, reads `refunded = 0`. Both compute `newTotal = 6,000 ≤ 10,000` and pass. Both call the gateway with different keys; it pays both: 12,000 out. Both write `setRefunded(6,000)`, a blind write, so the ledger says 6,000 while the network paid 12,000. The window is the full gateway round trip, about 20 ms here, not a nanosecond race, so at production QPS it happens routinely. The probe reproduces it in 20 of 20 trials."

</details>

<details><summary><b>Q3 · The interviewer, as the author: "It's synchronized and all tests pass. I think you're overthinking this."</b></summary>

**Initial Prompt.** Pushback from the author; tests the trust dimension.

**L5 Answer.** "No, it's definitely broken, synchronized doesn't work across instances." (Or caves: "OK, fair, maybe it's fine.")

**Why L5 Stalls.** Either escalates into a debate or abandons a Sev-1. Neither protects production or the relationship.

**L7 Answer.** "You're right that it's correct within one JVM, and the tests prove that well. My concern is specific: we run six replicas, and `synchronized` only coordinates threads inside one. Here's the interleaving [Q2]. Could we add a test with two `RefundService` instances sharing the stores? If it passes, I'll happily withdraw the comment. If it fails, the platform already has `tryReserve`, so the fix is small. Happy to pair on it." This turns a disagreement into an experiment the author controls.

</details>

<details><summary><b>Q4 · "Would `SELECT … FOR UPDATE` on the charge row fix F3 and F5?"</b></summary>

**Initial Prompt.** The classic L6 trap: a correct serialization that relocates the defect.

**L5 Answer.** "Yes, a database lock works across pods, so that fixes it."

**Why L5 Stalls.** It fixes F3's correctness but holds a row lock *and a pooled connection* for the full gateway round trip. During a gateway brownout (2 s timeouts), every refund holds a connection for 2 s. The pool drains, and every query in the service, and every service sharing the database, stalls. F5 moved from one pod's monitor to shared infrastructure.

**L7 Answer.** "It's correct and I'd still reject it. Never hold a lock across I/O you don't control, in the JVM or in the database. The conditional UPDATE (`tryReserve`) reserves the balance in one statement and releases the row at once. The gateway call happens with no lock held, and the outcome is settled by a second short write: success commits with the outbox, decline releases the reservation, timeout leaves it reserved as UNKNOWN for the reconciler."

</details>

<details><summary><b>Q5 · "Should this PR be blocked, or approved with comments?"</b></summary>

**Initial Prompt.** Review-state judgment.

**L5 Answer.** "Approve with comments. The author seems senior and will fix them."

**Why L5 Stalls.** Approval with an unresolved authz hole and a silent-corruption rename means the merge button is one click from an incident. "They'll fix it" is not a control.

**L7 Answer.** "Request changes, with an explicit, short list of blockers and everything else labeled non-blocking. Google's reviewer guide says to approve when a change definitely improves code health even if it isn't perfect. This PR makes the system *less* healthy on four axes: authz, ledger correctness, money conservation and durability. 'Request changes' is not a judgment of the author. It's the state that says 'not safe to merge yet.' I'd say that explicitly in the summary."

</details>

<details><summary><b>Q6 · "What would you add to CI so this class of bug never reaches a human reviewer again?"</b></summary>

**Initial Prompt.** Leverage beyond the diff (D8).

**L5 Answer.** "More unit tests."

**Why L5 Stalls.** Unit tests written by the same author encode the same model. That's how T1 happened. The question asks for *guardrails*, which work without anyone remembering them.

**L7 Answer.** "Four things, cheapest first. (1) Schema-registry compatibility check, BACKWARD or FULL, on every `refunds.*` subject, failing the build on a removed or renamed field: kills F8's class. (2) A metrics wrapper that only accepts label keys from an allowlist: kills F9's class. (3) A static rule (Error Prone or ArchUnit) flagging methods that are `synchronized` and call an interface annotated as remote, or lock-then-call patterns: catches F5. (4) A shared 'multi-instance' test fixture that builds two service instances on shared fakes, plus a gateway fake with a timeout-after-commit mode, offered to every service team. That's the one that catches F3, F4 and F6. The first two are a day each. I'd write the fourth as a platform proposal."

</details>

<details><summary><b>Q7 · "The ledger team says they agreed to switch to `amountMinor`. Is F8 still blocking?"</b></summary>

**Initial Prompt.** Social proof versus deploy ordering.

**L5 Answer.** "If they agreed, then it's fine."

**Why L5 Stalls.** Agreement is not deployment. Unless the ledger's change is deployed *before* this one, and every other consumer of `refunds.v1` is found, there is a window of silent zero-value refunds. Rollback of the ledger then re-breaks it.

**L7 Answer.** "Still blocking as written, cheap to unblock. Additive change: emit both `amountCents` and `amountMinor` on v1, let the ledger migrate on its own schedule, and remove `amountCents` only after the consumer registry shows no reader. Or publish v2 on a new topic. That makes deploy order irrelevant and rollback safe in both directions. I'd also check the schema registry or ACLs for consumers nobody remembers. There usually is one: a data-warehouse sink, a fraud model."

</details>

<details><summary><b>Q8 · "Suppose this shipped. How would you know, in production, that F6 had fired?"</b></summary>

**Initial Prompt.** Detection (D5): a fix you can't observe is a hope.

**L5 Answer.** "We'd see errors in the logs."

**Why L5 Stalls.** F6 produces *no* error for the money that moved. The 502 is logged, then the retry succeeds. Logs show one failure and one success, which looks healthy.

**L7 Answer.** "With an invariant check, not an error rate. Daily, ideally hourly: for each charge, Σ gateway payouts (from the network's settlement file or `lookup`) must equal our `refunded_minor`. Alarm on any non-zero delta, page on money-weighted deltas above a threshold. Supporting signals: the rate of RefundFailedException followed within 10 minutes by a SUCCEEDED refund on the same charge with a different key. Real retries of real failures don't look like that. After the fix, the signal becomes 'UNKNOWN rows older than N minutes', which the reconciler should drive to zero."

</details>

<details><summary><b>Q9 · "It's minute 30. You haven't opened the test file. What now?"</b></summary>

**Initial Prompt.** Time management and coverage (D7).

**L5 Answer.** Opens the tests and starts reviewing them line by line.

**Why L5 Stalls.** Spends the last 15 minutes on the lowest-yield file and never writes a summary.

**L7 Answer.** "Two minutes on the tests, aimed at one question: which tests *assert* behavior I've flagged as a bug? Those must change, or the fix will look like a regression. Here that's `gatewayTimeoutIsRetryable` and `publishesRefundIssuedEvent`. Then name the missing tests by scenario: two pods, timeout-after-commit, other merchant, max-value amounts. Then move to the summary at minute 40, whatever is left."

</details>

<details><summary><b>Q10 · "Is changing `int newTotal` to `long newTotal` enough for F2?"</b></summary>

**Initial Prompt.** Depth on a 'simple' fix.

**L5 Answer.** "Yes, long can hold 9 quintillion, so it won't overflow."

**Why L5 Stalls.** Fixes the comparison but not the persistence: `setRefunded(charge.id(), newTotal)` takes an `int`, so the write narrows or doesn't compile, and the schema column is `INT`. Also, the check remains check-then-act across pods (F3).

**L7 Answer.** "It fixes the comparison and nothing else. The value is persisted into an `INT` column through an `int` parameter, so either it won't compile or someone adds a cast that silently truncates. The right shape is to never compute `refunded + amount` in the application at all: the conditional UPDATE does BIGINT arithmetic in SQL and compares atomically, which fixes F2 and F3 together. Separately, I'd open a ticket to widen the column to BIGINT with an online migration, and add a property test with amounts near `Integer.MAX_VALUE`."

</details>
