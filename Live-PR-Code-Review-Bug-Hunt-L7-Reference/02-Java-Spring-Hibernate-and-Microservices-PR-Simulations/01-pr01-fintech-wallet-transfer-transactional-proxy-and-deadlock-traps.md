## 1. First principles: Spring transactions in six facts

1. **Proxies decide, not annotations.** Spring's reference: "In proxy mode (which is the default), only external method calls coming in through the proxy are intercepted. This means that self-invocation … does not lead to an actual transaction at runtime even if the invoked method is marked with `@Transactional`." Since Spring 6.0, `protected` and package-visible methods can be transactional on class-based proxies, but "only external method calls coming in through the proxy are intercepted" either way.
2. **Default rollback rules exclude checked exceptions.** "Any `RuntimeException` or `Error` triggers rollback, and any checked `Exception` does not." A checked exception thrown after a write *commits* that write unless `rollbackFor` says otherwise.
3. **A transaction pins a connection and every lock it takes, for its whole duration.** Anything slow inside it (HTTP, a sleep, a big computation) multiplies lock hold time and pool occupancy.
4. **Row-lock order is a global property.** PostgreSQL checks for deadlocks only after `deadlock_timeout` ("The default is one second"), then aborts one transaction (SQLSTATE 40P01). Spring translates that into a `PessimisticLockingFailureException`.
5. **Plain events are synchronous and inside the transaction.** `@EventListener` runs in the publisher's thread, before commit, and an exception from it propagates into the transaction. `@TransactionalEventListener` binds to a phase. The reference: "the listener is bound to the commit phase of the transaction by default", with `AFTER_COMMIT` as the default phase.
6. **Nested `REQUIRES_NEW` needs a second connection.** HikariCP's pool-sizing guide gives the minimum pool size that avoids pool-locking as "pool size = Tn x (Cm - 1) + 1", where Cm is the number of connections one thread holds at once. A naive "fix" of F1 (making `REQUIRES_NEW` actually work while the outer transaction holds a connection) changes Cm from 1 to 2.

## 2. The PR

> **WAL-2210 · P2P transfers between wallets**
>
> Users can send money from their wallet to another user's wallet. Requirements: (1) atomic, so both balances change or neither does; (2) every attempt is audited, *including failed and rejected ones* (AML/BSA); (3) fraud screening on the sender before money moves; (4) the recipient gets a push notification; (5) safe to retry with an `Idempotency-Key`.
>
> **PR description, by the author:**
> - `TransferService.transfer()` is `@Transactional`, so it is all-or-nothing.
> - Attempts are recorded in their own `REQUIRES_NEW` transaction, so they survive a rollback.
> - Wallet rows are locked with `SELECT … FOR UPDATE` to prevent lost updates.
> - The overdraft check uses the `RETURNING` balance from the debit: one round trip instead of two.
> - `InsufficientFundsException` is checked, so the controller is forced to map it to 422.
> - `NotificationListener` sends the push from a `TransferCompleted` event, decoupled from the service.
> - Duplicate idempotency keys are rejected by the unique constraint on `transfers.idempotency_key`.
> - Tests: happy path (balances, audit, push), overdraft, fraud rejection, duplicate key. All green.
>
> **Context the reviewer can discover:** 12 service replicas; HikariCP `maximumPoolSize=10`, `connectionTimeout=30s` in production (the probe uses 4 and 1 s to make the effect visible quickly); fraud-screening-service p50 40 ms, p99 1.8 s; the push provider has monthly incidents; wallets exist in USD, EUR and JPY.

```diff
+package com.acme.wallet;
+
+import org.springframework.context.ApplicationEventPublisher;
+import org.springframework.stereotype.Service;
+import org.springframework.transaction.annotation.Propagation;
+import org.springframework.transaction.annotation.Transactional;
+
+/**
+ * Peer-to-peer wallet transfers. Every attempt is audited (AML requirement), including attempts that fail, and the
+ * recipient is notified once the money has moved. Safe to retry with the same idempotency key.
+ */
+@Service
+public class TransferService {
+    public record TransferCompleted(long recipientOwnerId, long amountMinor, String currency) {}
+
+    private final WalletRepository wallets;
+    private final FraudClient fraud;
+    private final ApplicationEventPublisher events;
+
+    public TransferService(WalletRepository wallets, FraudClient fraud, ApplicationEventPublisher events) {
+        this.wallets = wallets;
+        this.fraud = fraud;
+        this.events = events;
+    }
+
+    /** Moves money atomically: either both balances change or neither does. Returns the transfer id. */
+    @Transactional
+    public long transfer(TransferCommand cmd) throws InsufficientFundsException {
+        recordAttempt(cmd); // own transaction (REQUIRES_NEW), so failed attempts stay audited
+        Wallet from = wallets.lockForUpdate(cmd.fromWalletId());
+        FraudVerdict verdict = fraud.screen(from.ownerId(), cmd.amountMinor(), from.currency());
+        if (!verdict.approved()) {
+            throw new TransferRejectedException(verdict.reason());
+        }
+        Wallet to = wallets.lockForUpdate(cmd.toWalletId());
+        long remaining = wallets.adjust(from.id(), -cmd.amountMinor()); // one round trip instead of read + write
+        if (remaining < 0) {
+            throw new InsufficientFundsException(from.id(), remaining + cmd.amountMinor(), cmd.amountMinor());
+        }
+        wallets.adjust(to.id(), cmd.amountMinor());
+        events.publishEvent(new TransferCompleted(to.ownerId(), cmd.amountMinor(), to.currency()));
+        return wallets.insertTransfer(cmd.idempotencyKey(), from.id(), to.id(), cmd.amountMinor());
+    }
+
+    @Transactional(propagation = Propagation.REQUIRES_NEW)
+    protected void recordAttempt(TransferCommand cmd) {
+        wallets.insertAudit(cmd.idempotencyKey(), "ATTEMPT " + cmd.fromWalletId() + "->" + cmd.toWalletId());
+    }
+}
```

## 5. The timed 3-pass diagnostic guide

### Minute 2: map and triage

- **Contracts changed:** a new money-moving endpoint. Callers retry (`Idempotency-Key`), 12 replicas run it, and there are two remote dependencies (fraud, push) plus a compliance requirement (audit failed attempts).
- **Hunk scores:** `TransferService.transfer` 8/8 (state, I/O, contract, trust); `recordAttempt` 6/8 (state, contract); `NotificationListener` 4/8 (I/O, contract); `TransferCommand` 2/8 (trust: caller-controlled amount).
- **Radar hits on sight:** `recordAttempt(cmd)` called on `this` with `REQUIRES_NEW` (line 29/45). `throws InsufficientFundsException` from a `@Transactional` method after a write (36–38). `fraud.screen` between two `lockForUpdate` calls (30–35). `publishEvent` before the last write (41–42). `insertTransfer` with the key as the *last* statement (42).

### Minute 10: one hop each

- Is `recordAttempt` called through the proxy? No: it's `this.recordAttempt`. The annotation is dead, so F1.
- What does Spring do with a checked exception? It commits. The debit at line 36 is then permanent: F2.
- Lock order: `from` then `to`. Two transfers in opposite directions take them in opposite orders: F3. The fraud call sits between them and widens the window to the fraud latency.
- What is held during `fraud.screen`? A pooled connection and the sender's row lock: F4.
- When does `@EventListener` run? Synchronously, inside the transaction: F5.
- What does a retry with the same key do? Re-runs everything and fails on the unique constraint: F6.
- `TransferCommand`: no validation. Negative amounts and cross-currency pairs go straight through: F7, F8.

### Minute 20: prove, unify, fix

- **Prove** each with a number or an interleaving (§6). The probes in §8 automate them.
- **Unify:** F1, F2, F4, F5 and F6 share one root cause. *The transaction boundary is drawn around the whole use case, including remote calls and side effects, instead of around the money movement alone.* Shrinking it to "lock, check, write, commit" (with audit before it, screening before it, notification after it, idempotency claimed first) fixes five defects with one design move. F3 is the classic lock-order fix. F7 and F8 are input validation.
- **Fix shape:** `TransferService` is the orchestrator (not transactional). `Ledger.move` is the only transaction, with `rollbackFor = Exception.class`, ordered locks and the idempotency claim first. The listener runs `AFTER_COMMIT`.

## 6. The L7 answer key, line by line

Line numbers refer to the new files on the `+` side. `TransferService.java` lines are the numbers inside that file (the `@@ -0,0 +1,49 @@` hunk).

### F1 · L3 · Sev-1 · Self-invoked `REQUIRES_NEW`: failed and rejected attempts are never audited (TransferService 29, 45–47)

**Mechanism.** `recordAttempt(cmd)` is a call on `this`, not on the Spring proxy, so its `@Transactional(propagation = REQUIRES_NEW)` never runs. The audit row is written *inside* the outer transaction, and any later rollback erases it: a fraud rejection, a deadlock, a duplicate key. These are exactly the attempts AML rules require you to keep. The comment on line 29 asserts the opposite of what happens, so a reader stops looking.

**Outage shape.** Regulatory, silent: the compliance team discovers in an audit that rejected transfers have no trail. Not detectable from error rates.

**Evidence.** P1: `fraud-rejected transfer -> TransferRejectedException; audit rows for the attempt = 0`. P3: after a deadlock, `audit rows = 1 of 2 attempts`.

```comment-l7
issue (blocking): `recordAttempt` is a self-call, so its REQUIRES_NEW never applies and rejected attempts are not audited

Line 29 calls `this.recordAttempt(...)`; Spring's proxy only intercepts external calls, so the audit insert joins the outer transaction and is rolled back with it. For example, a fraud rejection (line 33) throws a RuntimeException and the P1 probe finds 0 audit rows for the attempt; AML requires those rows. Suggest writing the attempt in its own transaction *before* the money transaction starts (a TransactionTemplate call from a non-transactional orchestrator), rather than nesting REQUIRES_NEW: nesting would need a second pooled connection per request while the first is held.
```

**Fix.** Audit commits on its own before the money transaction, never nested:
```java
    private void audit(TransferCommand cmd, String event) { // its own committed transaction, never nested
        tx.executeWithoutResult(status -> wallets.insertAudit(cmd.idempotencyKey(), event));
    }
```

### F2 · L3 · Sev-1 · A checked exception after the debit commits the debit: money is destroyed (TransferService 36–38)

**Mechanism.** The debit runs first (line 36, `RETURNING` the new balance). If the balance went negative, line 38 throws `InsufficientFundsException`, a **checked** exception. Spring's default rollback rules roll back only on `RuntimeException` and `Error`, so the transaction **commits**: the sender is debited, the recipient is never credited, and the caller is told "insufficient funds." The "one round trip" optimization in the PR description is what put the write before the check.

**Outage shape.** Silent money destruction on every overdraft attempt. The ledger's double-entry invariant (Σ balances is constant across a transfer) breaks, and the user sees a negative balance they never authorized.

**Evidence.** P2: `transfer 50,000 from a 10,000 wallet -> InsufficientFundsException; balances now -40,000 / 0; money in the system 10,000 -> -40,000`.

```comment-l7
issue (blocking): the overdraft path commits the debit, because InsufficientFundsException is checked

Line 36 debits first; line 38 then throws a checked exception, and Spring's default rollback rules only roll back on RuntimeException/Error, so the debit commits without the credit. The P2 probe shows it: a 50,000 transfer from a 10,000 wallet leaves the sender at -40,000 and the recipient at 0. The test `insufficientFundsIsReported` passes because it checks the exception, not the balances. Suggest deciding before any write (the row is already locked FOR UPDATE, so its balance is current) and declaring `rollbackFor = Exception.class` as a second line of defense; a CHECK (balance_minor >= 0) constraint would be a good third.
```

**Fix.**
```java
    @Transactional(rollbackFor = Exception.class) // checked exceptions roll back too
    public long move(TransferCommand cmd) throws InsufficientFundsException {
```
```java
        if (from.balanceMinor() < cmd.amountMinor()) { // decided before any write
            throw new InsufficientFundsException(from.id(), from.balanceMinor(), cmd.amountMinor());
        }
        wallets.adjust(from.id(), -cmd.amountMinor());
        wallets.adjust(to.id(), cmd.amountMinor());
```

### F3 · L2 · Sev-2 · Lock order follows the request direction: opposite transfers deadlock (TransferService 30, 35)

**Mechanism.** Each transfer locks `from` and then `to`. A→B locks A, then B; B→A locks B, then A. Interleaved, that is a cycle. PostgreSQL waits `deadlock_timeout` (1 s by default), aborts one transaction with 40P01, and Spring surfaces a `PessimisticLockingFailureException`. The fraud call between the two locks (line 31) widens the window from microseconds to the fraud latency, so it happens under ordinary traffic (two friends paying each other back at the same moment).

**Outage shape.** A share of transfers fail with 500s and pay a 1 s latency penalty first. Under load, deadlock storms and retry amplification follow.

**Evidence.** P3: `A->B || B->A with 150 ms fraud latency: 1 of 2 failed -> PessimisticLockingFailureException`.

```comment-l7
issue (blocking): opposite transfers lock the same two rows in opposite orders, which deadlocks

Line 30 locks the sender and line 35 the recipient, so A->B and B->A acquire {A, B} in opposite orders, which means each can end up waiting on the other. With the fraud call between the two locks, the window is the fraud latency: the P3 probe deadlocks on the first try (one transfer fails with PessimisticLockingFailureException after PostgreSQL's 1 s deadlock_timeout). Suggest locking both rows in one global order (lower id first), with nothing slow between the locks.
```

**Fix.**
```java
        Wallet low = wallets.lockForUpdate(Math.min(cmd.fromWalletId(), cmd.toWalletId())); // one global lock order
        Wallet high = wallets.lockForUpdate(Math.max(cmd.fromWalletId(), cmd.toWalletId()));
```

### F4 · L4 · Sev-2 · The fraud HTTP call runs inside the transaction, holding a row lock and a pooled connection (TransferService 27–31)

**Mechanism.** `@Transactional` acquires a connection before line 29 and holds it until commit. Line 30 takes the sender's row lock, and line 31 then waits on a network call (p99 1.8 s, timeout 3 s). Every in-flight transfer pins a connection for the fraud latency, and every other transfer touching that sender waits on the row lock. With 12 replicas × 10 connections, a fraud brownout turns into connection-pool exhaustion: `CannotCreateTransactionException` for *all* endpoints sharing the pool, not just transfers.

**Evidence.** P4: `16 concurrent transfers, pool 4, 400 ms fraud latency: N failed -> CannotCreateTransactionException` (one measured run; the fix: 0 failed).

```comment-l7
issue (blocking): the fraud call (line 31) runs while holding a pooled connection and the sender's row lock

`@Transactional` takes the connection before line 29 and the row lock at line 30, then waits on fraud-screening (p99 1.8 s). Under a fraud brownout every transfer pins a connection for the full call, which means the pool drains for every endpoint on this service. The P4 probe (pool 4, 400 ms latency, 16 concurrent) has requests failing with CannotCreateTransactionException; with screening moved before the transaction, none fail. ### F5 · L3 · Sev-2 · `@EventListener` fires inside the transaction: pushes for transfers that never happened, and a push outage blocks money (TransferService 41; NotificationListener 16–18)
```

**Mechanism.** `publishEvent` delivers synchronously to `@EventListener` methods, in the same thread and transaction. Two failure directions follow. (a) Anything that rolls back *after* line 41 (the duplicate-key insert on line 42, a commit failure) leaves a push already sent for money that never moved. (b) If the push provider throws, the exception propagates into `transfer()` and rolls back the money movement, so a third-party notification outage stops payments.

**Evidence.** P5: `client retries the same key: … recipient got 2 push(es) for 1 transfer(s)`. P6: `push provider down -> IllegalStateException; recipient balance 0`.

```comment-l7
issue (blocking): the push is sent before commit, and a push failure rolls back the transfer

`publishEvent` on line 41 runs `NotificationListener.on` synchronously inside this transaction. Two consequences: a retry that later fails on line 42 has already sent a push (P5 probe: 2 pushes for 1 transfer), and a push-provider outage throws into the transaction, which means payments stop when notifications are down (P6 probe: the transfer rolls back). Suggest `@TransactionalEventListener(phase = AFTER_COMMIT)` with failures counted rather than thrown, and, if delivery must be guaranteed, an outbox row in this transaction (PR06 covers that pattern).
```

**Fix.**
```java
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    public void on(TransferCompleted e) {
        try {
            push.send(e.recipientOwnerId(), "You received " + e.amountMinor() + " " + e.currency());
        } catch (RuntimeException ex) { // a push outage must not fail a committed transfer
            deliveryFailures.incrementAndGet();
        }
    }
```

### F6 · L3 · Sev-2 · Idempotency is enforced last: a retry redoes the work, fires side effects and gets a 500 (TransferService 42)

**Mechanism.** The idempotency key is first written by the *last* statement. A client retry (timeout, mobile reconnect) re-runs fraud screening, locks, debit, credit and the push, then hits the unique constraint, rolls back and returns `DuplicateKeyException`, a 500. The client never learns the original transfer id, and a client that treats 500 as "try again later" keeps retrying. The PR description calls this "safe to retry"; it is "safe from double debit, unsafe for everything else."

### F7 · L1 · Sev-1 · No currency check: 10.00 USD becomes 1,000 JPY (TransferService 30–40)

**Mechanism.** Both wallets are loaded but their currencies are never compared. Minor units are currency-relative: 1,000 minor units is 10.00 USD but ¥1,000 (JPY has no minor unit). A USD→JPY transfer silently converts at an arbitrary rate determined by the exponent difference. With EUR↔USD the rate is merely wrong; with JPY or KWD (3 decimals) it is off by orders of magnitude.

**Evidence.** P7: `USD wallet -> JPY wallet, 1,000 minor units -> transfer 1; JPY wallet now 1,000 yen`.

```comment-l7

This means value is created or destroyed by the exponent difference. ### F8 · L1/L6 · Sev-1 · Negative amounts reverse the transfer: the "sender" pulls money from the recipient (TransferCommand 4)
```

**Mechanism.** `amountMinor` comes from the request body and is never validated. **Evidence.** P8: `owner of wallet 1 'sends' -5,000 to wallet 2 -> transfer 1; balances now 5,000 / 0`.

```java
package com.acme.wallet;

import com.acme.wallet.TransferService.TransferCompleted;
import org.springframework.context.ApplicationEventPublisher;
import org.springframework.stereotype.Component;
import org.springframework.transaction.annotation.Transactional;

/** The money movement: one short transaction with no remote calls inside. A separate bean, so the proxy applies. */
@Component
public class Ledger {
    private final WalletRepository wallets;
    private final ApplicationEventPublisher events;

    public Ledger(WalletRepository wallets, ApplicationEventPublisher events) {
        this.wallets = wallets;
        this.events = events;
    }

    @Transactional(rollbackFor = Exception.class) // checked exceptions roll back too
    public long move(TransferCommand cmd) throws InsufficientFundsException {
        Long id = wallets.claimTransfer(cmd.idempotencyKey(), cmd.fromWalletId(), cmd.toWalletId(), cmd.amountMinor());
        if (id == null) {
            return wallets.findTransfer(cmd.idempotencyKey()); // a concurrent retry committed first
        }
        Wallet low = wallets.lockForUpdate(Math.min(cmd.fromWalletId(), cmd.toWalletId())); // one global lock order
        Wallet high = wallets.lockForUpdate(Math.max(cmd.fromWalletId(), cmd.toWalletId()));
        Wallet from = low.id() == cmd.fromWalletId() ? low : high;
        Wallet to = from == low ? high : low;
        if (!from.currency().equals(to.currency())) {
            throw new IllegalArgumentException("currency mismatch: " + from.currency() + " -> " + to.currency());
        }
        if (from.balanceMinor() < cmd.amountMinor()) { // decided before any write
            throw new InsufficientFundsException(from.id(), from.balanceMinor(), cmd.amountMinor());
        }
        wallets.adjust(from.id(), -cmd.amountMinor());
        wallets.adjust(to.id(), cmd.amountMinor());
        events.publishEvent(new TransferCompleted(to.ownerId(), cmd.amountMinor(), to.currency())); // after commit
        return id;
    }
}

package com.acme.wallet;

import org.springframework.stereotype.Service;
import org.springframework.transaction.support.TransactionTemplate;

/**
 * Peer-to-peer wallet transfers. Orchestrates, but is deliberately not @Transactional: audit rows commit on their own
 * before any money moves, fraud screening runs with no transaction and no lock, and the money movement itself is one
 * short transaction in {@link Ledger}. Safe to retry with the same idempotency key.
 */
@Service
public class TransferService {
    public record TransferCompleted(long recipientOwnerId, long amountMinor, String currency) {}

    private final WalletRepository wallets;
    private final FraudClient fraud;
    private final Ledger ledger;
    private final TransactionTemplate tx;

    public TransferService(WalletRepository wallets, FraudClient fraud, Ledger ledger, TransactionTemplate tx) {
        this.wallets = wallets;
        this.fraud = fraud;
        this.ledger = ledger;
        this.tx = tx;
    }

    /** Returns the transfer id; a replayed key returns the original id without side effects. */
    public long transfer(TransferCommand cmd) throws InsufficientFundsException {
        Long done = wallets.findTransfer(cmd.idempotencyKey());
        if (done != null) {
            return done;
        }
        audit(cmd, "ATTEMPT " + cmd.fromWalletId() + "->" + cmd.toWalletId());
        Wallet from = wallets.findById(cmd.fromWalletId()); // screening needs owner and currency only: no lock
        FraudVerdict verdict = fraud.screen(from.ownerId(), cmd.amountMinor(), from.currency());
        if (!verdict.approved()) {
            audit(cmd, "REJECTED " + verdict.reason());
            throw new TransferRejectedException(verdict.reason());
        }
        return ledger.move(cmd);
    }

    private void audit(TransferCommand cmd, String event) { // its own committed transaction, never nested
        tx.executeWithoutResult(status -> wallets.insertAudit(cmd.idempotencyKey(), event));
    }
}
```

### 7.1 Why this shape

| Concern | PR | Fix |
|---|---|---|
| Transaction boundary | The whole use case, including HTTP and the push | `Ledger.move` only: claim, lock, check, write |
| Audit of failures | Nested `REQUIRES_NEW` that never runs | A separate committed transaction *before* the money transaction; no nesting, so one connection per request at a time |
| Overdraft | Write, then check, then a checked exception commits the write | Check under the row lock, then write; `rollbackFor = Exception.class` |
| Lock order | Request direction | Global (lower id first) |
| Remote calls | Inside the transaction, holding a row lock | Before the transaction, holding nothing |
| Notification | Synchronous, before commit, can roll back money | `AFTER_COMMIT`, failures counted; an outbox (PR06) if delivery must be guaranteed |
| Idempotency | Unique constraint on the last statement | Replay check first, then `ON CONFLICT DO NOTHING` claim as the transaction's first write |
| Input | Unvalidated record | Compact-constructor validation: positive amount, distinct wallets; currency check under lock |

## 10. Failure modes (reviewers on this PR)

| Failure mode | What it looks like | Why it fails |
|---|---|---|
| Trusting annotations | "REQUIRES_NEW, good, failures are audited" | Proxy semantics decide; self-calls bypass |
| Exception = rollback | "It throws on overdraft, so nothing is written" | Checked exceptions commit by default |
| Fixing F1 by injecting `self` | `@Lazy TransferService self; self.recordAttempt(...)` | Makes REQUIRES_NEW real, *nested*: two connections per request; Hikari's pool-lock formula now applies |
| Fixing F3 with a retry loop | "Catch the deadlock and retry" | Retries treat the symptom, and a retry with a fresh transaction re-sends the push (F5) |
| Fixing F4 with a bigger pool | "Raise maximumPoolSize to 50" | Moves the bottleneck to PostgreSQL's `max_connections`, and row locks are still held for the fraud latency |
| Ignoring the event | "Decoupled via events, nice" | The decoupling is in code structure, not in time or failure domains |
| Reading tests as specs | "Tests cover overdraft and duplicates" | They assert exceptions, not state; one asserts the bug |

## 11. Bar-raiser chains

<details><summary><b>Q1 · "The author says: 'I'll fix F1 by self-injecting the proxy: `@Lazy @Autowired TransferService self;` then `self.recordAttempt(cmd)`.' Approve?"</b></summary>

**Initial Prompt.** Is the textbook workaround safe here?

**L5 Answer.** "Yes, calling through the proxy makes REQUIRES_NEW work."

**Why L5 Stalls.** It does make REQUIRES_NEW work, and that is the problem. The outer transaction already holds a pooled connection, and REQUIRES_NEW suspends it and borrows a second. With N concurrent transfers and a pool of N, every request holds one connection and waits for another: pool-locking until `connectionTimeout`. HikariCP's guide gives the minimum pool size as Tn × (Cm − 1) + 1.

**L7 Answer.** "It fixes the audit and introduces a pool deadlock under load: Cm goes from 1 to 2. Don't nest. The audit doesn't need to be inside the money transaction at all. Write it in its own short transaction *before* the money transaction starts, from a non-transactional orchestrator. One connection per request at a time, and the audit commits regardless of what follows."

</details>

<details><summary><b>Q2 · "Is `rollbackFor = Exception.class` enough for F2?"</b></summary>

**Initial Prompt.** Depth on the checked-exception fix.

**L5 Answer.** "Yes, now the debit rolls back."

**Why L5 Stalls.** It fixes this instance, but the design still writes before deciding. The next person who catches the exception inside the method, or calls it from a context where the proxy doesn't apply, recreates the bug.

**L7 Answer.** "Three layers. Decide before writing: the row is locked FOR UPDATE, so its balance is current. Keep `rollbackFor = Exception.class` as policy on money-moving methods; some teams enforce it with an ArchUnit rule. And add a database `CHECK (balance_minor >= 0)`, so an overdraft is impossible even if a future code path forgets. The database constraint is the only layer that protects against code that bypasses this service."

</details>

<details><summary><b>Q3 · "Prove the deadlock to me without running anything."</b></summary>

**Initial Prompt.** Interleaving construction.

**L5 Answer.** "Two transfers lock the same rows, so they can deadlock."

**Why L5 Stalls.** Two transfers A→B and A→B lock in the *same* order and merely queue. The candidate hasn't identified the cycle.

**L7 Answer.** "t0: T1 (A→B) locks A, then calls fraud for 150 ms. t1: T2 (B→A) locks B, then calls fraud. t2: T1 requests B and waits on T2. t3: T2 requests A and waits on T1. That's a cycle. After `deadlock_timeout` (1 s) PostgreSQL aborts one with 40P01. The fraud call between the locks makes the window the fraud latency, not microseconds, which is why the probe hits it on the first attempt."

</details>

<details><summary><b>Q4 · "Why not just catch `PessimisticLockingFailureException` and retry the transfer?"</b></summary>

**Initial Prompt.** Retry as a deadlock fix.

**L5 Answer.** "That's a standard pattern. Deadlocks are transient, so retry with backoff."

**Why L5 Stalls.** Retrying is reasonable as a safety net for *rare* serialization failures, not as the fix for a deterministic lock-order cycle. Here each retry also re-runs fraud screening and, in the PR's design, re-sends the push.

**L7 Answer.** "Fix the cause (a global lock order) so deadlocks between transfers become impossible. Keep a bounded retry for 40001/40P01 as defense in depth, but only around the *short* money transaction, and only once the side effects are outside it. Otherwise a retry repeats them."

</details>

<details><summary><b>Q5 · "The fraud team says screening must see the *current* balance. Doesn't that force the call inside the locked transaction?"</b></summary>

**Initial Prompt.** A requirement that seems to justify F4.

**L5 Answer.** "Then the call has to stay inside the transaction."

**Why L5 Stalls.** It accepts holding locks across I/O as the price of consistency. That price is pool exhaustion during every fraud brownout.

**L7 Answer.** "Screen on a snapshot outside the transaction, then re-validate the facts that matter under the lock: balance ≥ amount, and amount ≤ the limit the verdict approved. If the balance moved enough to change the verdict, reject or re-screen. That's optimistic concurrency applied to a remote decision. A fraud verdict is also usually a function of history plus amount, not of the exact balance at the microsecond of the debit. Holding a row lock for a 1.8 s p99 network call is not consistency, it's a queue."

</details>

<details><summary><b>Q6 · "Is `@TransactionalEventListener(AFTER_COMMIT)` enough to guarantee the recipient is notified?"</b></summary>

**Initial Prompt.** Delivery guarantees.

**L5 Answer.** "Yes, it runs after commit, so it only notifies for real transfers."

**Why L5 Stalls.** It fixes "notify for a rolled-back transfer" but not "never notify." If the JVM dies after commit and before the listener runs, or the push fails, the notification is lost. AFTER_COMMIT is at-most-once.

**L7 Answer.** "It gives at-most-once delivery, which is the right fix for this PR's bug: no phantom notifications, and push failures can't roll back money. If product needs at-least-once, write an outbox row in the money transaction and let a relay send and retry (PR06), with the recipient's client de-duplicating by transfer id. I'd note that as a follow-up, not a blocker, because a missed push is recoverable and a rolled-back payment isn't."

</details>

<details><summary><b>Q7 · "Two retries with the same key arrive at the same time on two pods. Walk me through the fixed code."</b></summary>

**Initial Prompt.** Idempotency under concurrency.

**L5 Answer.** "The first one inserts the key and the second gets a duplicate-key error."

**Why L5 Stalls.** That's the PR's behavior (a 500). The question is whether the fix converges.

**L7 Answer.** "Both pass the replay check (nothing committed yet), and both screen and audit, which is harmless and idempotent. In `Ledger.move`, both run `INSERT … ON CONFLICT DO NOTHING`. PostgreSQL makes the second insert *wait* on the first's uncommitted row. If the first commits, the second's insert does nothing and returns no row, and the code returns the committed transfer's id. If the first rolls back (say, insufficient funds), the second proceeds and gets its own decision. Both callers end up with one transfer and one id, and the money moves once."

</details>

<details><summary><b>Q8 · "What would you add to CI so this class of bug can't come back?"</b></summary>

**Initial Prompt.** Guardrails.

**L5 Answer.** "More integration tests."

**Why L5 Stalls.** Tests catch instances. The proxy and rollback semantics are *classes* of bug that recur in every new service.

**L7 Answer.** "Four cheap guards. (1) An ArchUnit rule: methods annotated `@Transactional` must not call other `@Transactional` methods on `this`, and money-moving services must declare `rollbackFor = Exception.class`. (2) An ArchUnit rule that `@Transactional` classes don't depend on HTTP-client interfaces, which catches F4's shape. (3) The database `CHECK (balance_minor >= 0)` plus a nightly double-entry invariant job (Σ balances = Σ funding − Σ withdrawals). (4) A shared test fixture with a slow fraud fake and two concurrent opposite transfers, so every payments team gets the deadlock test for free."

</details>

<details><summary><b>Q9 · "The PR description says 'one round trip instead of two' for the overdraft check. Is that optimization worth anything?"</b></summary>

**Initial Prompt.** Performance claims vs correctness.

**L5 Answer.** "Yes, fewer round trips is faster."

**Why L5 Stalls.** The saved round trip is about 0.2 ms inside a transaction that already waits 40–1,800 ms on fraud screening, and it is the reason F2 exists.

**L7 Answer.** "It saves a sub-millisecond round trip in a transaction dominated by a remote call, and it's what put the write before the check. In the fix the row is already locked and read, so the check costs zero round trips anyway. Micro-optimizations that reorder writes and checks in money code need a measured reason. This one had none."

</details>

<details><summary><b>Q10 · "Rank the eight findings for a release-train decision in 30 minutes."</b></summary>

**Initial Prompt.** Prioritization.

**L5 Answer.** "Deadlock first, it's the scariest."

**Why L5 Stalls.** The deadlock is loud and self-limiting (one side fails with a 500). The silent, money-moving defects are worse.

**L7 Answer.** "F8 (any user can drain any wallet: exploitable today), F2 (every overdraft destroys money, silently), F7 (cross-currency value creation), F1 (compliance, silent). Those four are Sev-1 and block. F4, F5, F6 and F3 are availability and side-effect issues that the same refactor fixes. If the train must leave, it leaves without WAL-2210 behind its flag. ## 12. Checklist

- [ ] Every `@Transactional` method: is it called through the proxy, or on `this`?
- [ ] Every checked exception thrown from a transactional method: does anything write before it, and is `rollbackFor` declared?
- [ ] Every method that locks two or more rows: is the lock order global (by id), not request-dependent?
- [ ] Every remote call: is it inside a transaction or under a lock? Move it out.
- [ ] Every `publishEvent`: is the listener `@EventListener` (inside the transaction) or `@TransactionalEventListener` (phase-bound)? Can a listener failure roll back money?
- [ ] Idempotency: is the key checked *before* any work and claimed as the first write?
- [ ] Input: positive amounts, distinct wallets, matching currencies, validated where the object is constructed.
- [ ] Tests: do failure-path tests assert database state, not just exceptions?
