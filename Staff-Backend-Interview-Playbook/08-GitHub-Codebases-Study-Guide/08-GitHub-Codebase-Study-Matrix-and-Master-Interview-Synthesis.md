## 0. How to use the matrix 🔥

Each row answers one question an interviewer can ask, and connects three things:

| Column | What it gives you |
|---|---|
| **Class (pinned)** | The file at the tag of the version you'd run, so line numbers match stack traces ([8.6 §0](06-Framework-Internals-by-Stack-Trace-Spring-Hibernate-HikariCP-Caffeine-Kafka.md)) |
| **Start at** | The method to read first, with its line, not the top of the file |
| **Question it answers** | The interview question this class lets you answer from evidence |
| **Kit** | The module where the behaviour was *measured*, so you can quote a number |

A row is "done" when you can say five bullets about the method and one critique, and point at the measurement. Twenty done rows across four pillars is a stronger L6 signal than a hundred skimmed files.

**Pins.** Versions follow the kit's verified stack: Spring Framework 7.0.10 (from the Boot 4.1.2 BOM), Hibernate 7.4.13, HikariCP 7.0.2, Kafka 4.2.2, Kubernetes v1.37.1 and the rest in §1. When you upgrade, re-pin and re-read the rows your service depends on; [8.7 §8](07-Source-Behind-the-Measurements-JDK-PostgreSQL-Redis-Kubernetes-Kafka.md) lists the lines most likely to matter.

### 10.3 The answer shape, written out once

Story 1 as a two-minute answer. The structure is what transfers:

> **Claim.** "Virtual threads moved our bottleneck from Tomcat's thread pool to the connection pool, and a design choice made it worse."
>
> **Mechanism.** "With platform threads, 200 Tomcat threads were an implicit bulkhead. With virtual threads, every request reaches the pool. And with Hikari's default auto-commit, Spring takes the connection in `JpaTransactionManager.doBegin`, so a `@Transactional` method holds it from its first line, including a pricing call we made before any SQL."
>
> **Evidence.** "In a thread dump the waiting requests were all in `ConcurrentBag.borrow` on the hand-off queue. Except the virtual ones weren't there at all: `getAllStackTraces()` doesn't include virtual threads, so we switched to the JSON thread dump. I reproduced it: pool of 2, four requests with a 1.5 s call inside the transaction, two timed out."
>
> **Trade-off.** "Lazy acquisition (`provider_disables_autocommit`) moves the borrow to the first query, but only if the pool really runs with auto-commit off. Moving the HTTP call out of the transaction fixes the cause."
>
> **Monday.** "HTTP calls outside transactions as a review rule, a semaphore sized from the database in front of the pool, and Hikari's pending-threads metric on the service dashboard."
