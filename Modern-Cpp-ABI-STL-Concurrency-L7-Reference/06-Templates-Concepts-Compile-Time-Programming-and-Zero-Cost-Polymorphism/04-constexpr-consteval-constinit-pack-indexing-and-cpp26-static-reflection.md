# 04 · `constexpr`, `consteval`, `constinit`, pack indexing, and C++26 static reflection

> **Scope.** Compile-time programming in C++ has three jobs: *compute* values during compilation (`constexpr`),
> *enforce* that something happens at compile time (`consteval`, the `std::format` technique), and *guarantee* that
> globals need no run-time initialization (`constinit`, the cure for the static-initialization-order fiasco). C++26
> reflection adds a fourth: *generating code from the program's own structure*. This file shows each in the object
> file or the compiler's diagnostics, and runs a reflection-based JSON serializer on GCC 16.

| # | Listing | What it proves | Verified by |
|---|---|---|---|
| 6.6 | `static_init.cpp` | `constinit`/`constexpr` globals are plain data; a dynamic global gets an initializer function; a function-local static gets a guard (plain `movzbl` on x86, `ldarb` on ARM64) and `__cxa_guard_*` calls; `constinit` rejects a non-constant initializer | asm x86-64 + AArch64; expected diagnostics |
| 6.7 | `consteval_check.cpp` | a format string checked against the argument count during compilation; `std::format` spec checking; `if consteval` | run + expected diagnostics |

## 1. First principles

### 1.1 Initialization in the object file (Listing 6.6)

```text
 static storage duration object        how it is initialized                 when
 ---------------------------------------  ------------------------------------  ----------------------------------
 constexpr / constinit / literal init    CONSTANT initialization: bytes in      at load time (the bytes are the
                                          .data/.rodata                          value); never "uninitialized"
 int g = compute();  (namespace scope)    zero-init, then DYNAMIC init by an     before main(), in an order that is
                                          initializer function (.init_array)     unspecified ACROSS translation units
 static T v = compute(); (in a function)  dynamic init on first call, guarded    first call, thread-safe since C++11
                                          by a guard byte + __cxa_guard_*        (Folder 08 has the guard protocol)
```

```cpp
// static_init.cpp - constant vs dynamic initialization in the object file: data, init functions, guards
int compute();                           // defined elsewhere: its value is unknown at compile time

int dynamic_global = compute();          // dynamic init: code in an initializer function, run before main()
constinit int const_global = 42;         // constant init (C++20 guarantees it, or the program is ill-formed)
constexpr int kSquares[4] = {0, 1, 4, 9};// constexpr: constant init AND usable in constant expressions

int read_dynamic() { return dynamic_global; }  // a plain load: but its value depends on init ORDER across TUs
int read_const() { return const_global; }      // a plain load of data that is never "not yet initialized"
int read_table(int i) { return kSquares[i & 3]; }

// Function-local statics: dynamic init happens on first call, thread-safe since C++11 ("magic statics").
int& local_dynamic() {
    static int v = compute();            // guard byte check (acquire) + __cxa_guard_acquire/release
    return v;
}
int& local_constinit() {
    static constinit int v = 7;          // constant-initialized: no guard at all
    return v;
}
#ifdef SHOW_CONSTINIT_ERROR
constinit int not_constant = compute();  // ill-formed: the initializer is not a constant expression
#endif
```

* `const_global`, `kSquares` and `local_constinit()::v` are **data** (`.long 42`, the table, `.long 7`). Reading them is a
  load, and no code ever runs to initialize them.
* `dynamic_global` is **zero in the file** (`.long 0`) and set by `_GLOBAL__sub_I_static_init.cpp`, the initializer
  function registered in `.init_array` (the trailing `.quad`/`.xword _GLOBAL__sub_I_...` line is that entry). Another
  TU's initializer that reads `dynamic_global` before this one has run sees 0: the **static-initialization-order
  fiasco**. Across TUs that order is unspecified.
* `local_dynamic()` checks its guard byte on every call. On **x86-64 that is a plain `movzbl`** (TSO makes ordinary loads
  acquire loads). On **AArch64 it is `ldarb`**, a load-acquire, so the thread that sees "initialized" also sees the
  initialized value. The slow path calls `__cxa_guard_acquire`/`__cxa_guard_release`, and the landing pad calls
  `__cxa_guard_abort` if `compute()` throws, so the next caller retries the initialization. The AArch64 code tests only bit
  0 (`tbz w8, #0`), per the guard-variable rule of the C++ ABI for the Arm 64-bit Architecture (CPPABI64); x86-64 tests
  the whole byte (`testb %al, %al`).
* `constinit` with a non-constant initializer is a compile error, which is the point: it turns "I hope this is constant"
  into a checked property (GCC, then Clang):

```text
static_init.cpp:22:15: error: 'constinit' variable 'not_constant' does not have a constant initializer
static_init.cpp:22:37: error: call to non-'constexpr' function 'int compute()'
static_init.cpp:22:15: error: variable does not have a constant initializer
```

### 1.2 Enforcing compile-time checks with `consteval` (Listing 6.7)

```cpp
// consteval_check.cpp - compile-time validation with consteval (the std::format technique) and if consteval
#include <cstddef>
#include <format>
#include <print>
#include <string_view>
#include <type_traits>
#include <utility>

// A format string whose placeholder count is checked against the argument count AT COMPILE TIME.
template <std::size_t N>
struct CheckedFmt {
    std::string_view text;
    consteval CheckedFmt(const char* s) : text(s) {   // implicit + consteval: runs during compilation
        std::size_t holes = 0;
        for (std::size_t i = 0; s[i]; ++i)
            if (s[i] == '{' && s[i + 1] == '}') ++holes;
        if (holes != N) throw "placeholder count does not match the number of arguments";  // -> compile error
    }
};
template <class... A>
void log_line(std::type_identity_t<CheckedFmt<sizeof...(A)>> fmt, A&&... args) {
    std::println("log: {} (+{} args)", fmt.text, sizeof...(args));
    ((std::print(" {}", std::forward<A>(args))), ...);
    std::println("");
}

// if consteval (C++23): one function, a constant-evaluation path and a run-time path.
constexpr unsigned popcount_any(unsigned x) {
    if consteval {
        unsigned c = 0;                // portable loop for the compiler
        for (; x; x &= x - 1) ++c;
        return c;
    } else {
        return static_cast<unsigned>(__builtin_popcount(x));  // popcnt / cnt when the target has it
    }
}
static_assert(popcount_any(0xF0F0u) == 8);

int main() {
    log_line("{} bought {} shares", "alice", 100);
    unsigned volatile v = 0xFFu;
    std::println("popcount_any(0xFF) at run time = {}", popcount_any(v));
#ifdef SHOW_CONSTEVAL_ERRORS
    log_line("{} bought {} shares", "alice");          // 2 placeholders, 1 argument: rejected while compiling
    auto s = std::format("{:d}", "not a number");      // std::format checks specs at compile time too
    (void)s;
#endif
}
```

Output (verified, both compilers):

```text
log: {} bought {} shares (+2 args)
 alice 100
popcount_any(0xFF) at run time = 8
```

With `-DSHOW_CONSTEVAL_ERRORS` (GCC, then Clang):

```text
consteval_check.cpp:45:26: error: call to consteval function 'std::basic_format_string<char, const char (&)[13]>("{:d}")' is not a constant expression
format:1388:48: error: call to non-'constexpr' function 'void std::__format::__failed_to_parse_format_spec()'
consteval_check.cpp:44:14: error: call to consteval function 'CheckedFmt<1>(((const char*)"{} bought {} shares"))' is not a constant expression
consteval_check.cpp:17:25: error: expression '<throw-expression>' is not a constant expression
consteval_check.cpp:45:26: error: call to consteval function 'std::basic_format_string<char, const char (&)[13]>::basic_format_string<char[5]>' is not a constant expression
consteval_check.cpp:44:14: error: call to consteval function 'CheckedFmt<1>::CheckedFmt' is not a constant expression
```

* **The technique behind `std::format`**: a parameter type with a `consteval` *converting* constructor. A string literal
  passed as the first argument is converted to `CheckedFmt<N>` *during compilation*, and the constructor validates it. A
  `throw` inside a `consteval` function is not a constant expression, so a bad string becomes a compile error at the call
  site. `std::type_identity_t` makes the first parameter a non-deduced context: `A...` is deduced from the remaining
  arguments only, and the literal is then converted to `CheckedFmt<sizeof...(A)>`. Without it, deduction would try to
  match `const char*` against `CheckedFmt<...>` and fail.
* `std::format("{:d}", "not a number")` is rejected the same way by both libraries' `basic_format_string`.
* **`if consteval`** (C++23) chooses an implementation by context: a portable loop during constant evaluation,
  `__builtin_popcount` at run time (one `popcnt` with `-mpopcnt` or `-march=x86-64-v2`, a NEON `cnt` + `addv` on
  AArch64, a bit-twiddling sequence on baseline x86-64). It replaces `std::is_constant_evaluated()`, which was easy to
  misuse (`if constexpr (std::is_constant_evaluated())` is always true).

### 1.3 Pack indexing: `Ts...[I]` instead of recursion (Folder 02, Listing 2.19)

Before C++26, "the I-th type of a pack" was a library construction: recursive specialization
(`nth<I, T, Ts...> : nth<I-1, Ts...>`), `std::tuple_element_t<I, std::tuple<Ts...>>`, or an overload-resolution trick.
Each of these makes the compiler instantiate a chain of class templates for every distinct `(I, Ts...)`, and the
compiler memoizes all of them for the rest of the TU. That is a compile-time and memory cost in heavily variadic code
(tuples, variant, type lists). P2662 makes indexing a core-language operation. This excerpt is from Listing 2.19, which
is verified on both compilers in Folder 02:

```text
template <std::size_t I, class... Ts>
constexpr auto nth(Ts... v) -> Ts...[I] { return v...[I]; }     // nth<2>(10, 'x', 3.5) == 3.5
```

* `Ts...[I]` is a type and `v...[I]` an expression. The index must be a constant expression; out of range is a compile
  error, so constrain public templates with `requires (I < sizeof...(Ts))` to get a readable diagnostic.
* With **structured-binding packs** (P1061, also in Listing 2.19: `auto [... xs] = t;`) a tuple-like object becomes a
  pack, so `std::apply` + lambda boilerplate shrinks to a fold over `xs`.
* Indexing with a *run-time* value still needs a dispatch table (the `std::visit` technique of file 03), because the
  result type depends on the index.

### 1.4 Reflection as a code generator (Listing 6.8)

```cpp
// reflect_json.cpp - C++26 reflection as a code generator: a generic to_json and a string -> enum parser
// GCC 16 with -std=c++26 -freflection.
#include <meta>
#include <optional>
#include <print>
#include <string>
#include <string_view>
#include <type_traits>
#include <vector>

enum class Side { buy, sell };

struct Fill {
    double price;
    int quantity;
};
struct Order {
    int id;
    std::string symbol;
    Side side;
    std::vector<Fill> fills;
};

template <class E>
    requires std::is_enum_v<E>
constexpr std::string_view enum_name(E v) {
    template for (constexpr auto e : std::define_static_array(std::meta::enumerators_of(^^E)))
        if (v == [:e:]) return std::meta::identifier_of(e);
    return "?";
}
template <class E>
    requires std::is_enum_v<E>
constexpr std::optional<E> enum_from(std::string_view s) {
    template for (constexpr auto e : std::define_static_array(std::meta::enumerators_of(^^E)))
        if (s == std::meta::identifier_of(e)) return [:e:];
    return std::nullopt;
}
static_assert(enum_from<Side>("sell") == Side::sell && !enum_from<Side>("hold"));

template <class T>
void to_json(std::string& out, const T& v) {
    if constexpr (std::is_same_v<T, std::string>) {
        out += '"';
        out += v;
        out += '"';
    } else if constexpr (std::is_enum_v<T>) {
        out += '"';
        out += enum_name(v);
        out += '"';
    } else if constexpr (std::is_arithmetic_v<T>) {
        out += std::to_string(v);
    } else if constexpr (requires { v.begin(); v.end(); }) {  // any range: an array
        out += '[';
        bool first = true;
        for (const auto& e : v) {
            if (!first) out += ',';
            first = false;
            to_json(out, e);
        }
        out += ']';
    } else {                                                  // an aggregate: one key per data member
        out += '{';
        bool first = true;
        constexpr auto ctx = std::meta::access_context::unchecked();
        template for (constexpr auto m : std::define_static_array(std::meta::nonstatic_data_members_of(^^T, ctx))) {
            if (!first) out += ',';
            first = false;
            out += '"';
            out += std::meta::identifier_of(m);
            out += "\":";
            to_json(out, v.[:m:]);
        }
        out += '}';
    }
}

int main() {
    Order o{42, "ACME", Side::buy, {{101.5, 10}, {101.25, 5}}};
    std::string json;
    to_json(json, o);
    std::println("{}", json);
    std::println("enum_from<Side>(\"buy\") -> {}", enum_name(*enum_from<Side>("buy")));
}
```

GCC 16.2, `-std=c++26 -freflection` (verified):

```text
{"id":42,"symbol":"ACME","side":"buy","fills":[{"price":101.5,"quantity":10},{"price":101.25,"quantity":5}]}
enum_from<Side>("buy") -> buy
```

* **One `to_json` for every aggregate**: `template for` expands over `nonstatic_data_members_of(^^T, ctx)` at compile time,
  `identifier_of(m)` gives the key, and `v.[:m:]` splices the member access. Nested structs and vectors recurse through
  ordinary `if constexpr` dispatch. There is no macro, no hand-written field list and no external code generator.
* **`enum_from<Side>("sell")`** is the inverse mapping, checked in a `static_assert`.
* The output shows `101.5`, not `101.500000`: GCC 16 implements the C++26 change (P2587) that defines `std::to_string` for
  floating-point types as `std::format("{}", v)` (shortest round-trip representation). Code that parses `to_string` output
  of doubles sees different strings than in C++23.
* Limits: reflection works on what the type *declares*. Invariants, units and versioning rules are not in the type.
  Access control is respected unless `access_context::unchecked()` is used deliberately. And only GCC implements it in
  this toolchain matrix.

## 3. Production blueprints

| Situation | Subtle buggy way | Production-hardened way |
|---|---|---|
| a global used by other TUs' initializers (registry, logger) | `Registry g_registry;` with a non-trivial constructor | `constinit` storage, or a function-local static (`Registry& registry() { static Registry r; return r; }`) |
| a lookup table | filled in `main()` or by a dynamic initializer | `constexpr` table (Folder 02, file 01: emitted as data) |
| validating literals (format strings, SQL, units) | run-time checks that fire in production | `consteval` constructors on the parameter type |
| a hot function-local static | `static T v = expensive();` called in a tight loop (a guard check per call, an acquire load on ARM64) | hoist the reference out of the loop, or make it `constinit` |
| enum ↔ string | hand-maintained switch statements | reflection (GCC 16), or a single X-macro table until reflection is available |

## 4. Failure modes

| Symptom | Root cause | Detection |
|---|---|---|
| a global is zero or default when read during start-up | static-initialization-order fiasco across TUs | `constinit` (compile error if not constant); function-local statics |
| deadlock in start-up | a function-local static's initializer calls the same function (recursive init) | libstdc++ throws `recursive_init_error`; Folder 08 |
| an exception in a static initializer, then "it works on retry" | `__cxa_guard_abort` resets the guard; the next call reinitializes | log and handle initializer failures explicitly |
| `consteval` error far from the actual problem | a value that must be constant flowed through a run-time variable | keep compile-time inputs as literals/`constexpr` up to the call |
| reflection code compiles only on GCC | P2996 not in Clang 21 | `__cpp_impl_reflection` guards; fallbacks |

## 5. Adversarial L7 bar-raiser chains

<details><summary><b>Chain 1 🔥 "What is the static initialization order fiasco?"</b></summary>

**Initial prompt.** "Explain the static initialization order fiasco and how to prevent it."

**L5 textbook answer.** "Globals in different files initialize in an unknown order, so use a singleton."

**Why L5 breaks.** The model is right; the remedy is incomplete. Listing 6.6 shows the mechanism: `dynamic_global` is 0 in
the object file and set by an initializer function in `.init_array`. If another TU's initializer reads it first, it sees
0. A "singleton" (function-local static) fixes the *order* but adds a guard check per access (an acquire load on ARM64)
and moves the problem to destruction order at exit. C++20 has a better tool for values that can be constant.

**L7 principal defense.** "`constinit` for every global that can be constant-initialized: the compiler proves it is data
(Listing 6.6), and the fiasco cannot happen. Function-local statics for the rest, with the reference hoisted out of hot
loops. For objects with destructors that others use at exit, deliberately leak them (`static T& t = *new T;`) to avoid the
destruction-order version of the problem."
</details>

<details><summary><b>Chain 2 ⚡ "Is a function-local static free after the first call?"</b></summary>

**Initial prompt.** "After initialization, does accessing a function-local static cost anything?"

**L5 textbook answer.** "No, it's initialized once and then it's a normal variable."

**Why L5 breaks.** Every call checks the guard byte (Listing 6.6: `movzbl` + `testb` + branch on x86; `ldarb` + `tbz` on
ARM64). On x86 it is nearly free. On ARM64 it is a load-acquire on every call, which constrains the reordering of later
loads. In a tight loop that adds up, and the compiler cannot hoist it, because it doesn't know whether the function is
called for the first time.

**L7 principal defense.** "Hoist the reference (`auto& cfg = config();` before the loop), or make the static `constinit`
when it can be constant (no guard at all: `local_constinit` is a single `lea`). For ARM64 hot paths, check for `ldar*`
instructions in the loop body."
</details>

<details><summary><b>Chain 3 🔥 "How does std::format reject bad format strings at compile time?"</b></summary>

**Initial prompt.** "`std::format("{:d}", "text")` fails to compile. How can a library function check a string literal at
compile time?"

**L5 textbook answer.** "The compiler has special support for format strings."

**Why L5 breaks.** No special support: the first parameter is `std::format_string<Args...>`, whose constructor is
`consteval`. Converting the literal runs the constructor during compilation; the parse fails and calls a non-`constexpr`
error function, which makes the call "not a constant expression" (Listing 6.7, GCC: `__failed_to_parse_format_spec`). Any
library can use the same technique, as `CheckedFmt` does.

**L7 principal defense.** "A `consteval` converting constructor on a parameter type, with `type_identity_t` to keep it out
of deduction. I'd use it for anything whose validity depends only on literals: log formats, SQL templates, unit-annotated
constants, protocol field layouts."
</details>

<details><summary><b>Chain 4 🧊 "constexpr vs consteval vs constinit, again"</b></summary>

**Initial prompt.** "Can you mark a variable `consteval`? What does `constinit` guarantee that `const` doesn't?"

**L5 textbook answer.** "`consteval` variables are compile-time constants, and `constinit` means const."

**Why L5 breaks.** Variables cannot be `consteval` (only functions). `constinit` does **not** imply `const`: the variable is
guaranteed constant-*initialized* and is mutable afterwards. `const` alone does not guarantee constant initialization (a
`const int x = compute();` global is dynamically initialized). `constexpr` on a variable implies both `const` and constant
initialization.

**L7 principal defense.** "`constexpr` for compile-time constants; `constinit` for mutable globals that must be ready before
any code runs (counters, allocator state, the root of a registry); `consteval` for functions that must never run at run
time. The object file (Listing 6.6) is the proof: data, not an initializer function."
</details>

<details><summary><b>Chain 5 ⚡ "What happens if a static initializer throws?"</b></summary>

**Initial prompt.** "A function-local static's constructor throws. What happens on the next call?"

**L5 textbook answer.** "The program terminates."

**Why L5 breaks.** Not for function-local statics. The exception propagates to the caller, and the landing pad calls
`__cxa_guard_abort` (Listing 6.6), which resets the guard, so the **next call tries to initialize again**. A namespace-scope
dynamic initializer that throws does call `std::terminate`, because nothing can catch it before `main`.

**L7 principal defense.** "Initialization that can fail should be explicit: return `expected` from an `init()` call made in
`main`, or make the static's initializer `noexcept` and record failure in state. Retry-on-next-call semantics are surprising
in production, especially with concurrent first callers (Folder 08 covers the guard protocol under contention)."
</details>

<details><summary><b>Chain 6 🔥 "What can C++26 reflection do?"</b></summary>

**Initial prompt.** "Write a function that serializes any aggregate struct to JSON."

**L5 textbook answer.** "Not possible without macros or a code generator."

**Why L5 breaks.** With C++26 static reflection it is ordinary C++ (Listing 6.8, running on GCC 16.2): iterate
`nonstatic_data_members_of(^^T)` with `template for`, emit `identifier_of(m)` as the key, recurse on `v.[:m:]`. Enums map to
names through `enumerators_of`, and the reverse mapping is a `consteval`-checkable function. The limits are what an L7
should add: compile-time only, only declared structure (no semantics), access control respected by default, and a
toolchain matrix where only GCC 16 has it today.

**L7 principal defense.** "Reflection replaces in-process code generation: serializers, printers, hashing, ORM mappings,
CLI flag parsing, test registration. Cross-language schemas stay schema-first. I'd adopt it behind a feature check with a
hand-written fallback until all our compilers ship P2996."
</details>

<details><summary><b>Chain 7 🧊 "if consteval vs is_constant_evaluated"</b></summary>

**Initial prompt.** "Why did C++23 add `if consteval` when `std::is_constant_evaluated()` exists?"

**L5 textbook answer.** "Syntax sugar."

**Why L5 breaks.** Two real problems. (1) `if constexpr (std::is_constant_evaluated())` is always `true`, because the
condition of `if constexpr` is itself constant-evaluated: a common bug. (2) Inside an `is_constant_evaluated()` branch you
still cannot call `consteval` functions, because the branch is not an immediate-function context. `if consteval` fixes both:
the first branch *is* a consteval context (Listing 6.7 uses it to pick a loop at compile time and `__builtin_popcount` at
run time).

**L7 principal defense.** "`if consteval` in new code; never `if constexpr (std::is_constant_evaluated())`. Both
compilers flag the old bug (checked on this toolchain): GCC 16 with `-Wtautological-compare` (in `-Wall`), *'always
evaluates to true in 'if constexpr''*; Clang 21 with `-Wconstant-evaluated` (on by default). Keep those warnings as
errors."
</details>

<details><summary><b>Chain 8 ⚡ "Compile-time cost"</b></summary>

**Initial prompt.** "Our build got 3× slower after moving lookup tables to `constexpr`. Why, and what can you do?"

**L5 textbook answer.** "constexpr is free at run time, so it's worth it."

**Why L5 breaks.** Free at run time, not at compile time. The constant evaluator interprets code step by step and tracks
every object's lifetime (which is what makes it a UB detector, Folder 01), so it is slow compared with native code.
Evaluating a large table in a header re-runs it in **every TU** that includes it. Limits like `-fconstexpr-steps` /
`-fconstexpr-ops-limit` exist because of this.

**L7 principal defense.** "Define big compile-time tables in one TU (or a module, which is evaluated once), expose them
through a declaration, and measure with `-ftime-trace` (Clang). For truly large data (megabytes), generate it at build time
or use `#embed` (C++26, P1967) rather than computing it in the constant evaluator."
</details>

## 6. Invariants checklist

- [ ] Globals used during start-up are `constinit`, or function-local statics; no cross-TU dynamic-initialization
      dependencies.
- [ ] Function-local static references are hoisted out of hot loops.
- [ ] Literal-only inputs are validated with `consteval` parameter types.
- [ ] `if consteval` instead of `std::is_constant_evaluated()`.
- [ ] Large compile-time tables are evaluated in one TU or module.
- [ ] Reflection is used behind `__cpp_impl_reflection` checks with fallbacks.
