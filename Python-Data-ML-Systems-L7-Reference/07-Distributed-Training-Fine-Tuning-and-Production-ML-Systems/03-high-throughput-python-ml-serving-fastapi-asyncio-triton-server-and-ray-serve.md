## 0. Orientation & the JVM/C++ Bridge

A model server has to answer one question: how to turn many small, independent requests into few large GPU calls without letting latency run away. Python adds two constraints a JVM engineer must internalize. The **event loop** is a single thread that must never block. The **GIL** serializes Python-level work, so a single process tops out at a few thousand requests per second however many threads it has. Everything else in this file (thread pools, dynamic batching, process-per-GPU, Triton's C++ core, Ray Serve's actors) is a way of working within those two facts.

| Python serving concept | JVM analogue | C++ analogue |
|---|---|---|
| asyncio event loop (uvicorn) | Netty / Vert.x event loop: never block it | epoll/IOCP reactor |
| `def` endpoint → Starlette thread pool (anyio, 40 tokens) | Spring MVC thread-per-request on a bounded Tomcat pool | a worker thread pool |
| dynamic batcher (`max_batch`, `max_wait`) | Kafka producer `batch.size` + `linger.ms` | Nagle-style coalescing |
| open-loop load generator | Gatling open injection; wrk2 / HdrHistogram (coordinated omission) | — |
| one GPU-owner thread/process | a single writer behind a queue (LMAX Disruptor) | an actor owning a device |
| Triton Inference Server | TF Serving / TorchServe class; a C++ server with model backends | the same |
| Ray Serve deployments + handles | Akka cluster actors + routers | — |

## 1. First Principles: C Memory Layout & Execution Architecture

### 1.1 The request path in a Python server

```text
 socket ─► uvicorn (ASGI server: asyncio loop thread, h11 HTTP parser)
        ─► Starlette routing ─► FastAPI: parse + validate body (pydantic-core, Rust) ─► endpoint
            async def endpoint   runs ON the event-loop thread: any blocking call stalls every connection
            def endpoint         run_in_threadpool → anyio CapacityLimiter(40) (anyio/_backends/_asyncio.py:3162)
        ─► response serialization ─► socket
 per request, Python-level work (parsing, validation, routing, JSON) holds the GIL for ~0.2-0.5 ms
   → one process ≈ 1-2.5k req/s on this CPU regardless of thread count (measured 1.1-2.4k)
 more throughput: more processes (uvicorn --workers N), but each loads its own model copy (N x GPU memory),
   or separate the HTTP front end from ONE GPU-owning batcher (the Triton design)
```

### 1.2 Queueing physics: why batching is the only lever that matters

```text
 service rate of one GPU call of batch b:  μ(b) = b / t(b)      measured t(1) = 0.37 ms, t(128) = 0.82 ms
   batch 1 → ≤ 2,700 req/s of GPU capacity; batch 128 → ~156,000 req/s (6.4 µs per request)
 utilization ρ = λ / μ;  M/D/1 mean wait W_q = ρ / (2 μ (1 - ρ))  → latency → ∞ as ρ → 1
 one-request-per-call measured: capacity ~1.8-1.9k/s (GPU + Python overhead), so at 2,000 offered p50 = 148-179 ms,
   at 6,000 offered p50 = 2.4 s and the backlog grows without bound
 greedy batching: when the GPU frees up, take EVERYTHING queued (up to max_batch). Batch size tracks load
   (measured mean 1.3 at 500/s → 4.0-4.2 at 6,000/s) with no timer → p99 ≈ 2.5-3.5 ms across the whole range
 window batching: wait up to W after the first request for more. Larger batches (28 at 6,000/s) but +W latency
   always; it pays only when t(b) is large relative to W or per-call overhead dominates
```

### 1.3 Batching strategies by workload

```text
 fixed-shape models (CV, tabular, embeddings): greedy or windowed dynamic batching, preferred sizes, CUDA Graphs
   per batch size (06.1)
 variable-length inputs: bucket by length and pad within a bucket (padding wastes FLOPs ∝ length variance)
 autoregressive LLMs: iteration-level ("continuous") batching. Sequences join and leave the batch at every
   decode step (Orca; vLLM), with a paged KV cache (07.2 §1.6) so memory follows actual lengths
```

### 1.4 Timers: a Windows-specific trap

```text
 Windows ProactorEventLoop waits with millisecond timeouts on the system tick (~15.6 ms by default):
   asyncio.sleep(1 ms) = 15.8-16 ms; asyncio.sleep(20 ms) ≈ 32 ms; wait_for(q.get(), 2 ms) ≈ 23 ms (measured)
   → a "2 ms" batching window silently becomes 16-23 ms of added latency
 timeBeginPeriod(1) (winmm, per process): asyncio.sleep(1 ms) → ~2-3 ms (measured)
 Linux hrtimer-based epoll timeouts are sub-millisecond (⚠ not measured here). Greedy batching needs no timer at all
```

### 1.5 NVIDIA Triton Inference Server (⚠ described, not run)

```text
 C++ server (no GIL on the hot path) ─ HTTP/REST + gRPC + in-process C API; system/CUDA shared-memory inputs
 model repository:  models/<name>/config.pbtxt + versions/1/model.{plan,onnx,pt,py}
 backends: TensorRT, ONNX Runtime, PyTorch (LibTorch), OpenVINO, Python backend (for glue code), vLLM/TRT-LLM
 per-model scheduler:
   dynamic_batching { preferred_batch_size: [ 8, 32 ]  max_queue_delay_microseconds: 500 }
   instance_group  [ { count: 2  kind: KIND_GPU } ]   ← 2 copies per GPU: overlap one's CPU work with the other's GPU work
 ensembles / BLS: pipelines of models inside the server (preprocess → model → postprocess) without client hops
 metrics: Prometheus (queue time, compute time, batch sizes); perf_analyzer for load tests
```

### 1.6 Ray Serve

```text
 HTTP proxy actor (per node) ─► router (power-of-two-choices over replicas) ─► replica actors (your class)
 @serve.batch(max_batch_size=10, batch_wait_timeout_s=0.01 by default, batching.py): per-replica windowed batching
 DeploymentHandle: call deployments from Python (composition: preprocess → model A → model B) without HTTP
 autoscaling on ongoing requests per replica; model multiplexing (many models per replica, LRU)
 every hop is a Ray task/actor call: serialization + scheduling + RPC
```

Measured on this single Windows node, the per-request framework path cost milliseconds, more than the ~1 ms CPU model: **~150–200 req/s through the HTTP proxy, ~300–380 req/s through handles**. A second replica and `@serve.batch` (mean batch 2.3–2.8) changed little because replicas weren't the bottleneck. ⚠ Linux, multiple proxies and gRPC ingress raise the ceiling. The lesson is to measure the framework's own ceiling before attributing latency to the model.

## 2. The Slow Pythonic Trap vs. the L7 Production Pattern

### 2.1 The batcher at the core of every server

```python
"""asyncio_dynamic_batcher.py - the core of every model server: an asyncio front end feeding a GPU through a batcher.

A: GPU cost vs batch size for a 4-layer fp16 MLP (width 2048): per call and per item.
B: Windows timers: asyncio sleeps and timeouts round up to the ~15.6 ms system tick unless timeBeginPeriod(1).
C: open-loop Poisson load (requests arrive whether or not the server keeps up) against three dispatch policies:
     one request per GPU call | greedy batching (take everything queued) | a 2 ms batching window
   throughput, p50/p99 latency (from scheduled arrival to result) and mean batch size.
The model runs in one dedicated executor thread, so the event loop never blocks on the GPU.
"""
import asyncio
import concurrent.futures
import ctypes
import time

import numpy as np
import torch

dev = torch.device("cuda")
torch.manual_seed(0)
D = 2048
model = torch.nn.Sequential(*[m for _ in range(4) for m in (torch.nn.Linear(D, D), torch.nn.GELU())]).to(dev).half().eval()
pool = torch.randn(256, D).half().pin_memory()           # request payloads (reused rows)


def infer(rows):
    with torch.inference_mode():
        x = torch.stack(rows).to(dev, non_blocking=True)
        return model(x).float().sum(dim=1).cpu()         # .cpu() waits for the GPU


print("== A. GPU cost vs batch size")
for b in (1, 8, 32, 128):
    rows = [pool[i] for i in range(b)]
    infer(rows)
    t0 = time.perf_counter()
    for _ in range(50):
        infer(rows)
    dt = (time.perf_counter() - t0) / 50
    print(f"  batch {b:4d}: {dt * 1e3:6.3f} ms per call, {dt / b * 1e6:8.1f} us per request")


async def sleep_ms(d):
    ts = []
    for _ in range(20):
        t0 = time.perf_counter()
        await asyncio.sleep(d / 1e3)
        ts.append(time.perf_counter() - t0)
    return sorted(ts)[10] * 1e3


print("== B. asyncio timer granularity on Windows (ProactorEventLoop)")
print(f"  asyncio.sleep(1 ms) takes {asyncio.run(sleep_ms(1)):.2f} ms (median); asyncio.sleep(2 ms) {asyncio.run(sleep_ms(2)):.2f} ms")
winmm = ctypes.windll.winmm
winmm.timeBeginPeriod(1)                                 # 1 ms system timer for this process (reverted at exit)
print(f"  after timeBeginPeriod(1): asyncio.sleep(1 ms) {asyncio.run(sleep_ms(1)):.2f} ms; "
      f"asyncio.sleep(2 ms) {asyncio.run(sleep_ms(2)):.2f} ms  (section C runs with this setting)")


class Server:
    def __init__(self, policy, max_batch=128, window_ms=2.0):
        self.q = asyncio.Queue()
        self.policy, self.max_batch, self.window = policy, max_batch, window_ms / 1e3
        self.gpu = concurrent.futures.ThreadPoolExecutor(max_workers=1)
        self.batches = []

    async def submit(self, row):
        fut = asyncio.get_running_loop().create_future()
        await self.q.put((row, fut))
        return await fut

    async def run(self):
        loop = asyncio.get_running_loop()
        while True:
            items = [await self.q.get()]                 # block until at least one request
            if self.policy == "window":
                deadline = loop.time() + self.window
                while len(items) < self.max_batch and (left := deadline - loop.time()) > 0:
                    try:
                        items.append(await asyncio.wait_for(self.q.get(), left))
                    except TimeoutError:
                        break
            if self.policy != "single":
                while len(items) < self.max_batch and not self.q.empty():
                    items.append(self.q.get_nowait())    # greedy: everything that queued up meanwhile
            out = await loop.run_in_executor(self.gpu, infer, [r for r, _ in items])
            self.batches.append(len(items))
            for (_, fut), y in zip(items, out.tolist()):
                fut.set_result(y)


async def load_test(policy, rate, seconds=2.0):
    server = Server(policy)
    worker = asyncio.create_task(server.run())
    rng = np.random.default_rng(int(rate))
    arrivals = np.cumsum(rng.exponential(1 / rate, int(rate * seconds)))
    lat, tasks = [], []

    async def one(t_sched, i):
        await server.submit(pool[i % len(pool)])
        lat.append(time.perf_counter() - t_sched)

    t_start = time.perf_counter()
    for i, t in enumerate(arrivals):
        now = time.perf_counter() - t_start
        if t > now:
            await asyncio.sleep(t - now)                 # open loop: launch on schedule, never wait for results
        tasks.append(asyncio.create_task(one(t_start + t, i)))
    await asyncio.wait_for(asyncio.gather(*tasks), timeout=60)
    elapsed = time.perf_counter() - t_start
    worker.cancel()
    lat_ms = np.array(lat) * 1e3
    return len(lat) / elapsed, np.percentile(lat_ms, 50), np.percentile(lat_ms, 99), np.mean(server.batches)


print("== C. open-loop load: offered rate -> achieved rate, latency, batch size")
print(f"  {'policy':26} {'offered/s':>9} {'achieved/s':>10} {'p50 ms':>8} {'p99 ms':>8} {'mean batch':>10}")
res = {}
for policy, label in (("single", "one request per GPU call"), ("greedy", "greedy batching (<=128)"),
                      ("window", "2 ms batching window")):
    for rate in (500, 2000, 6000):
        thr, p50, p99, mb = asyncio.run(load_test(policy, rate))
        res[policy, rate] = (thr, p50, p99, mb)
        print(f"  {label:26} {rate:9d} {thr:10.0f} {p50:8.2f} {p99:8.2f} {mb:10.1f}")
winmm.timeEndPeriod(1)
assert res["greedy", 6000][2] < res["single", 6000][2] / 5
print("ALL ASSERTIONS PASSED")
```

### 2.2 FastAPI over HTTP: event loop, thread pool, batcher

```python
"""fastapi_event_loop.py - FastAPI/uvicorn serving a GPU model: blocking the event loop vs threadpool vs batching.

The server runs in a subprocess (uvicorn, asyncio loop, h11) with four endpoints on one GPU model:
  POST /blocking    async def that calls the model inline   -> the event loop stalls for every GPU call
  POST /threadpool  plain def: Starlette runs it in its worker-thread pool (anyio, 40 threads by default)
  POST /batched     async def awaiting a greedy dynamic batcher (one executor thread owns the GPU)
  GET  /health      returns immediately: its latency under load measures event-loop responsiveness
The client is a minimal HTTP/1.1 keep-alive client on asyncio streams (httpx's AsyncClient was itself the bottleneck
above ~8 connections here): 32 concurrent connections, closed loop, one endpoint at a time for 3 s, while a probe on
its own connection calls /health every ~5 ms.
"""
import asyncio
import concurrent.futures
import ctypes
import os
import socket
import subprocess
import sys
import time

D = 2048


def build_app():
    import torch
    from fastapi import FastAPI
    from pydantic import BaseModel

    dev = torch.device("cuda")
    torch.manual_seed(0)
    model = torch.nn.Sequential(*[m for _ in range(4) for m in (torch.nn.Linear(D, D), torch.nn.GELU())]).to(dev).half().eval()
    row = torch.randn(D).half()

    def infer(n):
        with torch.inference_mode():
            x = row.expand(n, D).to(dev)
            return model(x).float().sum(dim=1).cpu().tolist()

    infer(1)
    gpu = concurrent.futures.ThreadPoolExecutor(max_workers=1)
    queue: asyncio.Queue = asyncio.Queue()
    sizes = []

    async def batcher():
        loop = asyncio.get_running_loop()
        while True:
            futs = [await queue.get()]
            while len(futs) < 128 and not queue.empty():
                futs.append(queue.get_nowait())
            out = await loop.run_in_executor(gpu, infer, len(futs))
            sizes.append(len(futs))
            for f, y in zip(futs, out):
                f.set_result(y)

    app = FastAPI()

    class Req(BaseModel):
        x: float = 0.0

    @app.on_event("startup")
    async def start():
        asyncio.get_running_loop().create_task(batcher())

    @app.post("/blocking")
    async def blocking(r: Req):
        return {"y": infer(1)[0]}                         # GPU work on the event-loop thread

    @app.post("/threadpool")
    def threadpool(r: Req):
        return {"y": infer(1)[0]}                         # sync endpoint: run in a worker thread

    @app.post("/batched")
    async def batched(r: Req):
        fut = asyncio.get_running_loop().create_future()
        await queue.put(fut)
        return {"y": await fut}

    @app.get("/health")
    async def health():
        return {"ok": True}

    @app.get("/stats")
    async def stats():
        return {"mean_batch": sum(sizes) / max(len(sizes), 1)}

    return app


def serve(port):
    import uvicorn
    ctypes.windll.winmm.timeBeginPeriod(1)
    uvicorn.run(build_app(), host="127.0.0.1", port=port, log_level="warning", loop="asyncio", http="h11")


class Conn:
    """One keep-alive HTTP/1.1 connection: send a request, read status + Content-Length body."""

    def __init__(self, port):
        self.port = port

    async def open(self):
        self.r, self.w = await asyncio.open_connection("127.0.0.1", self.port)
        return self

    async def call(self, method, path, body=b""):
        head = f"{method} {path} HTTP/1.1\r\nHost: x\r\nContent-Type: application/json\r\nContent-Length: {len(body)}\r\n\r\n"
        self.w.write(head.encode() + body)
        await self.w.drain()
        hdr = await self.r.readuntil(b"\r\n\r\n")
        assert hdr.startswith(b"HTTP/1.1 200"), hdr[:40]
        n = int(next(ln.split(b":")[1] for ln in hdr.split(b"\r\n") if ln.lower().startswith(b"content-length")))
        return await self.r.readexactly(n)

    def close(self):
        self.w.close()


async def drive(port, path, seconds=3.0, conc=32):
    import json

    import numpy as np

    lat, health = [], []
    users = [await Conn(port).open() for _ in range(conc)]
    hc = await Conn(port).open()
    stop = time.perf_counter() + seconds

    async def user(c):
        while time.perf_counter() < stop:
            t0 = time.perf_counter()
            await c.call("POST", path, b'{"x": 1.0}')
            lat.append(time.perf_counter() - t0)

    async def probe():
        while time.perf_counter() < stop:
            t0 = time.perf_counter()
            await hc.call("GET", "/health")
            health.append(time.perf_counter() - t0)
            await asyncio.sleep(0.005)

    await asyncio.gather(probe(), *[user(c) for c in users])
    mb = json.loads(await hc.call("GET", "/stats"))["mean_batch"] if path == "/batched" else 1.0
    for c in users + [hc]:
        c.close()
    lat_ms, h_ms = np.array(lat) * 1e3, np.array(health) * 1e3
    return len(lat) / seconds, np.percentile(lat_ms, 50), np.percentile(lat_ms, 99), np.percentile(h_ms, 99), mb


def main():
    with socket.socket() as s:
        s.bind(("127.0.0.1", 0))
        port = s.getsockname()[1]
    srv = subprocess.Popen([sys.executable, os.path.abspath(__file__), "--serve", str(port)],
                           stdout=subprocess.DEVNULL, stderr=subprocess.DEVNULL)
    try:
        import httpx
        for _ in range(120):
            try:
                httpx.get(f"http://127.0.0.1:{port}/health", timeout=1).raise_for_status()
                break
            except httpx.HTTPError:
                time.sleep(0.5)
        ctypes.windll.winmm.timeBeginPeriod(1)
        print("== closed loop, 32 keep-alive connections, 3 s per endpoint (uvicorn + FastAPI, one RTX 3050)")
        print(f"  {'endpoint':12} {'req/s':>8} {'p50 ms':>8} {'p99 ms':>8} {'/health p99 ms':>15} {'mean batch':>11}")
        res = {}
        for path in ("/blocking", "/threadpool", "/batched"):
            asyncio.run(drive(port, path, seconds=0.5))  # warm-up
            res[path] = asyncio.run(drive(port, path))
            thr, p50, p99, h99, mb = res[path]
            print(f"  {path:12} {thr:8.0f} {p50:8.2f} {p99:8.2f} {h99:15.2f} {mb:11.1f}")
        assert res["/batched"][0] > res["/blocking"][0]
        assert res["/batched"][3] < res["/blocking"][3]
        print("ALL ASSERTIONS PASSED")
    finally:
        srv.terminate()
        srv.wait(timeout=30)


if __name__ == "__main__":
    if len(sys.argv) > 2 and sys.argv[1] == "--serve":
        serve(int(sys.argv[2]))
    else:
        main()
```

* `/blocking` (GPU call inside `async def`): **every other request waits** while the loop thread is in the GPU call. `/health` p99 was ~23–30 ms, a liveness probe that fails under load.
* `/threadpool` (`def`) kept the loop responsive (`/health` p99 ~10–13 ms) but didn't add throughput: 40 threads contend for the GIL and the GPU, one request per call.
* `/batched` gave **~1.6–1.9× the throughput** (1.8–2.4k req/s) at ~2/3 the p50, with mean batch ~13. Now the HTTP/pydantic work per request is the ceiling, which is the signal to add front-end processes in front of one GPU owner, or move to a C++ server.

### 2.3 Ray Serve: replicas, `@serve.batch`, handles

```python
"""ray_serve_batching.py - Ray Serve: deployments, replicas and @serve.batch behind Serve's HTTP proxy.

Three deployments of the same CPU model (3-layer MLP, width 1024, one torch thread per replica):
  /single    one request per model call, 1 replica
  /replicas  one request per model call, 2 replicas (Serve load-balances across replica actors)
  /batched   @serve.batch(max_batch_size=32, batch_wait_timeout_s=0.002), 1 replica
Load A: 32 keep-alive HTTP/1.1 connections (asyncio streams) through Serve's HTTP proxy, closed loop, 3 s per route.
Load B: the same 32-way concurrency through DeploymentHandles from the driver (no HTTP proxy: router -> replica RPC).
Each replica raises the Windows timer resolution (timeBeginPeriod(1)) so the 2 ms batch window means 2 ms.
"""
import asyncio
import ctypes
import os
import socket
import sys
import time

import numpy as np
import ray
from ray import serve
from starlette.requests import Request


def make_model():
    import torch
    torch.set_num_threads(1)
    torch.manual_seed(0)
    return torch.nn.Sequential(torch.nn.Linear(1024, 1024), torch.nn.GELU(), torch.nn.Linear(1024, 1024),
                               torch.nn.GELU(), torch.nn.Linear(1024, 1)).eval()


@serve.deployment
class Single:
    def __init__(self):
        import torch
        ctypes.windll.winmm.timeBeginPeriod(1)
        self.torch, self.model, self.row = torch, make_model(), torch.ones(1, 1024)

    async def __call__(self, request: Request):
        await request.body()
        return await self.infer(1)

    async def infer(self, _):
        with self.torch.inference_mode():
            return {"y": self.model(self.row).item(), "batch": 1}


@serve.deployment
class Batched:
    def __init__(self):
        import torch
        ctypes.windll.winmm.timeBeginPeriod(1)
        self.torch, self.model, self.row = torch, make_model(), torch.ones(1, 1024)

    @serve.batch(max_batch_size=32, batch_wait_timeout_s=0.002)
    async def predict(self, items):
        with self.torch.inference_mode():
            y = self.model(self.row.expand(len(items), 1024)).squeeze(1).tolist()
        return [{"y": v, "batch": len(items)} for v in y]

    async def __call__(self, request: Request):
        await request.body()
        return await self.predict(1)

    async def infer(self, x):
        return await self.predict(x)


class Conn:
    def __init__(self, port):
        self.port = port

    async def open(self):
        self.r, self.w = await asyncio.open_connection("127.0.0.1", self.port)
        return self

    async def call(self, path):
        body = b'{"x": 1.0}'
        head = f"POST {path} HTTP/1.1\r\nHost: x\r\nContent-Type: application/json\r\nContent-Length: {len(body)}\r\n\r\n"
        self.w.write(head.encode() + body)
        await self.w.drain()
        hdr = await self.r.readuntil(b"\r\n\r\n")
        assert hdr.startswith(b"HTTP/1.1 200"), hdr[:60]
        lengths = [ln.split(b":")[1] for ln in hdr.split(b"\r\n") if ln.lower().startswith(b"content-length")]
        if lengths:
            return await self.r.readexactly(int(lengths[0]))
        body = b""                                       # Transfer-Encoding: chunked
        while (size := int((await self.r.readuntil(b"\r\n")).strip(), 16)) > 0:
            body += await self.r.readexactly(size)
            await self.r.readexactly(2)
        await self.r.readexactly(2)
        return body


async def drive(port, path, seconds=3.0, conc=32):
    import json
    conns = [await Conn(port).open() for _ in range(conc)]
    lat, sizes = [], []
    stop = time.perf_counter() + seconds

    async def user(c):
        while time.perf_counter() < stop:
            t0 = time.perf_counter()
            sizes.append(json.loads(await c.call(path))["batch"])
            lat.append(time.perf_counter() - t0)

    await asyncio.gather(*[user(c) for c in conns])
    for c in conns:
        c.w.close()
    ms = np.array(lat) * 1e3
    return len(lat) / seconds, np.percentile(ms, 50), np.percentile(ms, 99), float(np.mean(sizes))


async def drive_handle(handle, seconds=3.0, conc=32):
    lat, sizes = [], []
    stop = time.perf_counter() + seconds

    async def user():
        while time.perf_counter() < stop:
            t0 = time.perf_counter()
            sizes.append((await handle.infer.remote(1))["batch"])
            lat.append(time.perf_counter() - t0)

    await asyncio.gather(*[user() for _ in range(conc)])
    ms = np.array(lat) * 1e3
    return len(lat) / seconds, np.percentile(ms, 50), np.percentile(ms, 99), float(np.mean(sizes))


def main():
    with socket.socket() as s:
        s.bind(("127.0.0.1", 0))
        port = s.getsockname()[1]
    ray.init(num_cpus=6, include_dashboard=False, log_to_driver=False, logging_level="ERROR")

    serve.run(Single.options(num_replicas=2).bind(), name="replicas", route_prefix="/replicas")

    ctypes.windll.winmm.timeBeginPeriod(1)
    print("== A. through Serve's HTTP proxy, 32 keep-alive connections, 3 s per route (CPU model, 1 torch thread per replica)")
    print(f"  {'route':10} {'req/s':>8} {'p50 ms':>8} {'p99 ms':>8} {'mean batch':>11}")

        finally:
            sys.stdout.flush()                           # drop what Ray buffered while fd 1 pointed at devnull
```

## 3. Production Failure Modes & Debugging

| # | Symptom | Signature | Root cause | Fix | Prevention |
|---|---|---|---|---|---|
| F1 🔥 | All requests slow, health checks fail, pods restarted | Event-loop lag ≈ model latency; `/health` p99 tens of ms | Blocking call (GPU, `requests`, file I/O) in `async def` | `run_in_executor` / `def` endpoints / batcher | `loop.slow_callback_duration` + asyncio debug mode in staging; a loop-lag metric |
| F2 | Latency jumps at ~40 concurrent requests | Requests queued in anyio | Thread-pool limit (CapacityLimiter 40) | Raise the limiter deliberately, or go async/batched | Load-test at production concurrency |
| F3 🔥 | GPU OOM after scaling workers | N processes × model copy | `uvicorn --workers N` loads N models | One GPU-owner process + front ends, or Triton instance groups | GPU memory budget per pod |
| F4 🔥 | p99 explodes near peak traffic | Queue depth grows without bound | ρ → 1 with no admission control | Bounded queues, 429/503 shedding, deadlines per request | Autoscale on queue depth/concurrency, not CPU |
| F5 | Load test says p99 = 20 ms, production says 2 s | Closed-loop client | Coordinated omission: slow responses slow the generator | Open-loop arrivals; latency from scheduled time | Open-loop tooling (wrk2, Gatling open model, the listing's generator) |
| F6 ⚠ | A "2 ms" batch window adds 16 ms | Windows host | System timer tick 15.6 ms | `timeBeginPeriod(1)`, greedy batching, or Linux | Measure the batcher's real wait |
| F7 ⚡ | Batched variable-length requests slower than expected | Padding to the longest | Shape variance | Length buckets, ragged/nested kernels | Track padding ratio |
| F8 ⚡ | Throughput flat although the GPU is idle | Per-request `.item()`/`.cpu()` | One sync per request | Sync once per batch; return results in bulk | Profile the request path for syncs |
| F9 | Ray Serve far below model capacity | Proxy/handle overhead ≫ model time | ms-scale framework path per request | Client-side batching, gRPC ingress, more proxies; leaner server for hot paths | Benchmark the framework with a no-op model first |
| F10 🔥 | First requests after deploy time out | Model load + `torch.compile` per shape | Cold start on the request path | Warm up all buckets before readiness (06.3) | Readiness probe gated on warm-up |

**Debugging toolkit.** Event-loop lag probes (a coroutine that sleeps 10 ms and records overshoot); `asyncio` debug mode (`PYTHONASYNCIODEBUG=1`, logs callbacks > 100 ms); per-request timestamps for queue time vs compute time; batch-size histograms; `py-spy dump` on a stuck worker (⚠ not run); Triton's `perf_analyzer` and Prometheus metrics; Ray dashboard and `serve status`; open-loop generators with HdrHistogram-style percentiles.

## 4. L7 Bar-Raiser Q&A Chains

<details><summary><b>Q1 · "Our FastAPI model server falls over at 1,000 QPS."</b></summary>

**Initial Prompt.** A PyTorch model behind FastAPI; p99 is fine at 300 QPS and collapses at 1,000.

**L5 Answer.** "Python is slow. Add more uvicorn workers."

**Why L5 Crashes at Scale.** More workers multiply GPU memory (one model copy each) and still run one request per GPU call, so the GPU's per-call overhead stays the bottleneck. If the endpoint is `async def` calling the model inline, every worker's event loop blocks during inference, so health checks fail and orchestrators restart pods under load.

**L7 Principal Defense.** First check where the time goes: event-loop lag, per-request queue vs compute time, batch size. Measured on one GPU: GPU work inline in `async def` gave 1.1–1.3k req/s with `/health` p99 ~25 ms. A sync `def` endpoint kept health responsive but added no throughput. A **dynamic batcher** behind the loop (requests enqueue a future; one executor thread owns the GPU and takes everything queued) gave 1.8–2.4k req/s with mean batch ~13. Beyond that the per-request Python HTTP work is the ceiling, so add front-end processes that forward to one GPU owner, or use a C++ server (Triton) for the hot path. Add admission control (bounded queue, 503 with retry-after) so overload degrades gracefully.

</details>

<details><summary><b>Q2 · "Design a dynamic batcher."</b></summary>

**Initial Prompt.** Specify the batching component of an inference server.

**L5 Answer.** "Collect requests for 10 ms, then run them together."

**Why L5 Crashes at Scale.** A fixed window adds its full duration to every request at low load (measured: a 2 ms window gave ~4–6 ms p50 vs ~1.3 ms greedy), and on Windows "10 ms" silently becomes ~16–32 ms. It also says nothing about the queue bound, deadlines, errors or shapes.

**L7 Principal Defense.** Use a bounded `asyncio.Queue` of `(payload, future, deadline)` and a single GPU-owner task: block for the first item, then drain greedily up to `max_batch` (optionally wait up to a small window only when the measured per-call cost is large), run the model in an executor thread, and resolve each future. Drop expired requests before compute. Propagate exceptions to every future in the failed batch. Bucket by shape (pad within a bucket). Expose batch-size and queue-time histograms. It's Kafka's producer design: `batch.size` = `max_batch`, `linger.ms` = window. Measured: greedy served 6k/s at p99 ~2.5–2.9 ms with batch size adapting from 1.3 to 4.0–4.2 as load rose.

</details>

<details><summary><b>Q3 · "p99 explodes at 70 % of the capacity our load test reported."</b></summary>

**Initial Prompt.** Load tests said the service handles 2,000 QPS; production melts at 1,400.

**L5 Answer.** "Production traffic is burstier; add 50 % headroom."

**Why L5 Crashes at Scale.** Headroom is guesswork if the measurement is wrong. A closed-loop load test (N clients each waiting for a response) slows down when the server does, so it never queues requests and under-reports latency: coordinated omission. Real users arrive regardless.

**L7 Principal Defense.** Use open-loop Poisson arrivals and measure latency from the **scheduled** arrival time, as the listing does. Then the queueing curve is visible: one request per call saturated at ~1.8–1.9k/s, and at 2,000 offered p50 was 148–179 ms; at 6,000 it was 2.3–2.4 s and growing. Plot latency against offered load to find the knee, set SLO capacity well below it (M/D/1: wait ∝ ρ/(1-ρ)), and raise the knee itself with batching. Validate with production-like burstiness (replayed traces), and autoscale on queue depth or in-flight requests, which move before CPU does.

</details>

<details><summary><b>Q4 · "`async def` or `def` for FastAPI endpoints?"</b></summary>

**Initial Prompt.** Team guideline needed.

**L5 Answer.** "Always `async def`: it's faster."

**Why L5 Crashes at Scale.** `async def` runs on the event-loop thread. Any blocking call there (GPU inference, `requests.get`, a sync DB driver, heavy CPU) stalls every connection in the process (measured: `/health` p99 23–30 ms behind GPU calls).

**L7 Principal Defense.** Use `async def` only when everything inside awaits non-blocking I/O (async DB/HTTP clients, `await queue`). Use `def` for blocking libraries: Starlette runs it in a 40-thread pool (anyio's default limiter), which keeps the loop responsive but adds no GPU throughput (measured ~1.15–1.3k req/s, like inline). Use a process pool for CPU-heavy Python (GIL). Send GPU inference through a batcher owned by one executor thread (measured 1.6–1.9× throughput). Enforce it in CI with asyncio debug mode and a loop-lag test.

</details>

<details><summary><b>Q5 · "Triton Inference Server, FastAPI or Ray Serve?"</b></summary>

**Initial Prompt.** Pick the serving stack for a new platform.

**L5 Answer.** "FastAPI: everyone knows it."

**Why L5 Crashes at Scale.** Familiarity isn't a requirement. The stacks differ in where the hot path runs (Python vs C++), how batching and model instances are managed, and what composition and autoscaling they give.

**L7 Principal Defense.** **Triton**: C++ hot path, per-model dynamic batching and instance groups, TensorRT/ONNX/LibTorch backends, shared-memory inputs, ensembles. Pick it for high-QPS, latency-critical models that export cleanly; Python only as glue (⚠ not run here). **FastAPI + your own batcher**: maximum control and simplest ops for one or a few models; ceiling ~1–2.5k req/s per process from Python overhead (measured), so scale with front-end processes and one GPU owner. **Ray Serve**: multi-model composition, autoscaling, heterogeneous CPU/GPU pipelines on a Ray cluster. Measured per-request overhead was ms-scale here (~150–380 req/s single node), so put tiny-model hot paths elsewhere or batch at the client. Many platforms combine them: Ray Serve or FastAPI for orchestration, Triton or vLLM for the GPU-heavy steps.

</details>

<details><summary><b>Q6 · "Why is static batching wrong for LLM serving?"</b></summary>

**Initial Prompt.** An LLM endpoint batches 16 prompts and generates until all finish.

**L5 Answer.** "Bigger batches give higher throughput."

**Why L5 Crashes at Scale.** Output lengths vary by 10–100×. A static batch runs until its longest sequence ends, so short requests wait for long ones (bad latency) and finished slots sit idle (bad throughput). The KV cache preallocated for max length wastes most memory (07.2 §1.6).

**L7 Principal Defense.** Use iteration-level (continuous) batching: at every decode step the scheduler removes finished sequences and admits waiting ones, so the batch stays full. Pair it with a paged KV cache (blocks on demand, prefix sharing) and admission control by KV budget. Separate the metrics: time to first token (prefill, compute-bound, benefits from FP8/large batches) vs time per output token (decode, bandwidth-bound, benefits from int4 weights with fused kernels, 07.2, and CUDA Graphs per batch size, 06.3). Chunked prefill stops long prompts from stalling everyone's decode. This is what vLLM, TensorRT-LLM and SGLang do. Building it yourself means re-deriving all of it.

</details>

<details><summary><b>Q7 · "Autoscale a GPU inference service on Kubernetes."</b></summary>

**Initial Prompt.** HPA on CPU utilization scales too late; GPU pods take minutes to start.

**L5 Answer.** "Scale on GPU utilization instead."

**Why L5 Crashes at Scale.** GPU utilization saturates early with batching (a busy GPU at 30 % or 90 % load looks the same), and it says nothing about latency. Cold pods also need model download, load, compile and warm-up before they can serve.

**L7 Principal Defense.** Scale on **queue depth or in-flight requests per replica** against a latency SLO. Those move first and map directly to the queueing curve. Keep warm capacity for burst lead time (pod start + model load + warm-up, measured in seconds to minutes; 06.3 Q6). Cut cold start with images that carry weights and compile caches and readiness gated on warm-up. Shed load explicitly when beyond capacity. Within a pod, one GPU-owner batcher per GPU, and a front-end process count sized to the Python request overhead.

</details>

<details><summary><b>Q8 · "Ray Serve gives 200 req/s; the model takes 1 ms."</b></summary>

**Initial Prompt.** A team migrated to Ray Serve and lost 10× throughput.

**L5 Answer.** "Add replicas and enable `@serve.batch`."

**Why L5 Crashes at Scale.** Measured here, neither helped: 2 replicas went 172–202 req/s and `@serve.batch` (mean batch 2.3–2.5) 160–180. Replicas weren't the bottleneck. The per-request path (HTTP proxy actor → router → replica actor, each hop serialized and scheduled) was, at milliseconds per request.

**L7 Principal Defense.** Benchmark the framework with a no-op model first. That sets the ceiling. Removing the HTTP proxy (handles) roughly doubled throughput here (294–382 req/s), which locates the cost. Options: batch at the client (one request carries many items), gRPC ingress, more proxies on more nodes, or keep the high-QPS, tiny-model path in a lean server (FastAPI + batcher measured 1.8–2.4k req/s on the same machine). Use Ray Serve where its abstractions earn their overhead: multi-stage pipelines, many models, autoscaling across a cluster. ⚠ Linux clusters will show different absolute numbers. The method of measuring the framework separately from the model transfers.

</details>

<details><summary><b>Q9 · "How do you load-test an inference service correctly?"</b></summary>

**Initial Prompt.** Define the methodology for a service's capacity sign-off.

**L5 Answer.** "Run 100 concurrent clients and report the average latency."

**Why L5 Crashes at Scale.** Concurrency-based (closed-loop) clients hide queueing (coordinated omission). Averages hide tails. A single load level hides the knee, so the reported capacity is optimistic in exactly the regime that causes incidents.

**L7 Principal Defense.** Open-loop arrivals (Poisson or replayed traces) at a sweep of offered rates; latency measured from scheduled arrival; p50/p99/p99.9 per level after warm-up; achieved vs offered throughput (divergence means overload); batch-size and queue-time histograms from the server; resource traces (GPU busy, CPU per process, event-loop lag). The listing's table is that method in miniature: it shows the one-request-per-call policy's knee at ~1.8–1.9k/s and greedy batching's flat p99 up to 6k/s. Also test overload behaviour (shedding, recovery), cold start, and real payload sizes. The deliverable is a latency-vs-load curve with the SLO line on it, not a single number.

</details>

## 5. Invariants Checklist

- [ ] Never block the event loop. Blocking work goes to threads (`def`), processes (CPU) or a GPU-owner executor.
- [ ] Batching is the throughput lever: GPU cost per request fell 58× from batch 1 to batch 128 here.
- [ ] Greedy batching adapts to load with no timer. Windowed batching always adds its window.
- [ ] On Windows, asyncio timers have ~15.6 ms granularity unless `timeBeginPeriod(1)`.
- [ ] One Python process handles ~1–2.5k req/s. Scale front ends separately from the GPU owner.
- [ ] Load-test open-loop, report tails against offered load, and find the knee.
- [ ] Measure framework overhead with a no-op model before blaming the model.
- [ ] LLMs need continuous batching and a paged KV cache, not static batches.
