## 1. Cloud Storage configuration checklist

| Setting | Recommended practice | Why |
|---|---|---|
| **Location** | Region for co-located processing; dual-region for geo-redundancy with control over the two regions; multi-region for wide serving | Latency, cost, residency (P1, P10) |
| **Default storage class / Autoclass** | **Autoclass** when access is unknown; otherwise a default class plus lifecycle rules | Cost (P9) |
| **Uniform bucket-level access** | Enable (IAM only, no ACLs) | Simpler, auditable access |
| **Public access prevention** | Enforce (org policy `storage.publicAccessPrevention`) | Stops accidental public buckets |
| **Soft delete** | Keep the default (7 days) or set the retention you need | Recover deleted objects |
| **Versioning** | Enable for critical data + lifecycle to expire noncurrent versions | Recover overwrites without unbounded cost |
| **Retention policy / Bucket Lock** | For regulatory WORM | Immutability (can't be shortened once locked) |
| **Encryption** | Default, or CMEK via Cloud KMS when custody is required | P11 |
| **Turbo replication** (dual-region) | When a 15-minute RPO for cross-region replication is required | DR |
| **Rapid Cache** (formerly Anywhere Cache) | For read-heavy workloads in a specific zone (analytics, AI training) | Throughput, lower egress from multi-regions |

### Lifecycle rules: an example

Aging media (Altostrat-style) when access patterns **are** predictable:

```json
{
  "lifecycle": {
    "rule": [
      {"action": {"type": "SetStorageClass", "storageClass": "NEARLINE"},
       "condition": {"age": 30, "matchesStorageClass": ["STANDARD"]}},
      {"action": {"type": "SetStorageClass", "storageClass": "COLDLINE"},
       "condition": {"age": 90, "matchesStorageClass": ["NEARLINE"]}},
      {"action": {"type": "SetStorageClass", "storageClass": "ARCHIVE"},
       "condition": {"age": 365, "matchesStorageClass": ["COLDLINE"]}},
      {"action": {"type": "Delete"},
       "condition": {"daysSinceNoncurrentTime": 30, "isLive": false}}
    ]
  }
}
```

```bash
# Apply lifecycle rules (predictable aging)
gcloud storage buckets update gs://altostrat-media --lifecycle-file=lifecycle.json

# Or let Google move each object by its own access pattern (unpredictable access)
gcloud storage buckets create gs://altostrat-media-v2 --location=us --enable-autoclass

# Compliance archive: 7-year WORM retention, then lock it (irreversible)
gcloud storage buckets update gs://ehr-audit-archive --retention-period=7y
gcloud storage buckets update gs://ehr-audit-archive --lock-retention-period
```

**Exam facts**

* **Autoclass and `SetStorageClass` lifecycle rules don't mix.** Autoclass manages classes itself; you can still use `Delete` rules.
* Lifecycle transitions only move "colder" (Standard → Nearline → Coldline → Archive). They don't move data back to warmer classes; Autoclass can.
* A **locked** retention policy can't be removed or reduced, and the bucket can't be deleted until every object meets retention.

### Access patterns

| Need | Configure |
|---|---|
| A partner uploads files without a Google account, for 1 hour | **Signed URL** (V4) for PUT, generated by a service account |
| Read-only access for an analytics team to one bucket | IAM `roles/storage.objectViewer` on the bucket to a **group** |
| Website assets publicly readable | Public via IAM `allUsers` objectViewer on a dedicated bucket, ideally behind Cloud CDN / LB backend bucket (keep public access prevention on for every other bucket) |
| Prevent copying data out of the organization | VPC Service Controls perimeter |
| Event-driven processing on upload | Pub/Sub notifications or Eventarc triggers on object finalize |

## 2. Block storage configuration

| Decision | Guidance |
|---|---|
| Disk type | `pd-balanced` as the default; `pd-ssd` / Hyperdisk Balanced or Extreme for databases; Hyperdisk Throughput for streaming and analytics; Hyperdisk ML for model loading by many VMs |
| Performance model | PD performance scales with size (and vCPU); **Hyperdisk** lets you **provision IOPS and throughput independently** of capacity |
| HA | **Regional PD / Hyperdisk Balanced HA** synchronously replicates across two zones (failover a stateful VM in about a minute) |
| Snapshots | **Snapshot schedules** (resource policies) with retention; store in multi-regional or regional locations; snapshots are incremental |
| Faster recovery | Instant snapshots (local, fast restore) plus standard snapshots (durable, off-disk) |
| Ephemeral speed | Local SSD for scratch. Data is lost on stop or host failure, so replicate or rebuild |
| Encryption | Default, CMEK or CSEK (CSEK is rarely the best answer) |

## 3. Database configuration essentials

### Cloud SQL

* **HA (regional)** configuration: primary + standby in another zone, synchronous replication, automatic failover.
* **Edition:** Enterprise vs **Enterprise Plus** (higher performance, data cache, 99.99% SLA including maintenance, near-zero-downtime maintenance, longer PITR).
* **Backups:** automated daily backups + **point-in-time recovery**; on-demand backups before risky changes; retain backups after instance deletion when required.
* **Read replicas** (same region, cross-region) to offload reads and for DR; **cascading replicas**.
* **Storage auto-increase** with a limit (growth planning; storage can't shrink).
* **Maintenance windows** and deny periods.
* **Connectivity:** private IP (PSA or PSC), **Cloud SQL Auth Proxy / language connectors** (IAM-based, TLS); **IAM database authentication**; managed connection pooling.
* **Query Insights** for performance troubleshooting.

### BigQuery

* **Dataset location** fixed at creation (residency; co-locate with sources).
* **Partitioning** (by ingestion time, date/timestamp column or integer range) and **clustering** (up to 4 columns) to cut bytes scanned.
* **Table and partition expiration** for lifecycle; **long-term storage** pricing applies automatically to tables or partitions unmodified for 90 days.
* Storage billing model: logical vs **physical (compressed)** per dataset.
* **Editions** (Standard / Enterprise / Enterprise Plus) with autoscaling slot reservations vs **on-demand** per-TB pricing; set **custom quotas** to cap on-demand spend.
* Access: dataset/table IAM, **authorized views / authorized datasets**, **row-level security**, **column-level security** with policy tags, **dynamic data masking**.

```sql
-- Lifecycle inside BigQuery: drop partitions older than 400 days
ALTER TABLE analytics.events SET OPTIONS (partition_expiration_days = 400);
```

### Spanner, Bigtable, Firestore, Memorystore

| Service | Configure |
|---|---|
| Spanner | Instance configuration (regional / dual-region / multi-region); compute capacity in **nodes or processing units** with **autoscaling**; backups and PITR (version retention up to 7 days); edition (Standard / Enterprise / Enterprise Plus) |
| Bigtable | Clusters (zones), nodes and **autoscaling**, SSD vs HDD storage, **replication** + app profiles (single- vs multi-cluster routing), garbage-collection policies per column family (lifecycle), backups |
| Firestore | Location (regional / multi-region) fixed at creation; **TTL policies** to expire documents; PITR; scheduled backups; security rules (client access) and IAM (server access) |
| Memorystore | HA tier / replicas, persistence (RDB/AOF) where supported, cluster mode, maintenance windows, AUTH and in-transit encryption |

## 4. Transfer and latency configuration

| Need | Configuration |
|---|---|
| Fast large uploads | `gcloud storage cp` (parallel composite uploads), or Storage Transfer Service agents with bandwidth limits |
| Recurring on-premises → cloud file sync | Storage Transfer Service with agent pools, scheduled jobs and bandwidth caps |
| Petabyte one-time move | Transfer Appliance |
| Low-latency reads from compute | Co-locate bucket and compute in one region; Rapid Cache for hot data |
| Serving to the world | Multi-region bucket + Cloud CDN / Media CDN |
| Database replicas near readers | Cross-region read replicas (Cloud SQL, AlloyDB secondary clusters), Spanner read-only replicas |

## 5. Data growth planning

* Estimate growth (per day/month) and plan **quotas** and **limits**: Cloud SQL max storage, Bigtable nodes per cluster, BigQuery slot needs, Spanner nodes.
* Choose stores that **scale horizontally** when growth is open-ended (Spanner, Bigtable, BigQuery, Cloud Storage).
* Use **autoscaling** for Spanner and Bigtable, and storage auto-increase for Cloud SQL.
* Enforce **lifecycle and retention** from day one, so growth is bounded by policy rather than by forgotten data.
* Monitor with **Storage Insights**, BigQuery INFORMATION_SCHEMA, Cloud Monitoring metrics and budgets.

## 6. Data protection summary (backup and recovery)

| Data | Protect with |
|---|---|
| VM disks | Snapshot schedules; machine images; **Backup and DR Service** with **backup vaults** (immutable) |
| GKE workloads | **Backup for GKE** |
| Cloud SQL / AlloyDB | Automated backups + PITR; cross-region replicas |
| Spanner / Firestore / Bigtable | Native backups (+ PITR for Spanner/Firestore) |
| BigQuery | Time travel (7 days), fail-safe, table snapshots, dataset replication |
| Cloud Storage | Soft delete, versioning, retention + Bucket Lock, dual/multi-region |
| Ransomware resilience | **Immutable** backups (backup vaults with enforced retention, Bucket Lock), separate project and IAM for backups, tested restores |

---

## 7. Traps

* **Lifecycle `SetStorageClass` rules on an Autoclass bucket.**
* **Locking a retention policy "to test it".** Locking is irreversible.
* **Cloud SQL storage over-provisioned "to be safe".** Storage can't shrink; use auto-increase with a cap.
* **BigQuery tables without partitioning** for time-series queries (cost and performance).
* **Backups in the same project, region and IAM boundary as production** (one compromise destroys both).
* **Granting `roles/storage.admin` when `objectViewer` or `objectCreator` suffices.**
