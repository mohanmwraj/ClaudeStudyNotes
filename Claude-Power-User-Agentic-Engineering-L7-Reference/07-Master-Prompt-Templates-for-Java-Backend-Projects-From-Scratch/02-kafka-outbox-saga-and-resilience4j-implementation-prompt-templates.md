## 0. Orientation

The most common data-integrity bug in event-driven Java services is one line:

```java
@Transactional
public Order place(PlaceOrder cmd) {
    Order o = orderRepository.save(Order.from(cmd));
    kafkaTemplate.send("orders.order-events.v1", o.id().toString(), OrderPlaced.of(o));   // the dual write
    return o;
}
```

Two systems are being written with no shared transaction:
- **If the commit fails after the send,** consumers act on an order that doesn't exist (a *ghost* event).
- **If the process dies after the commit but before the producer flushes,** the order exists and nobody hears about it (a *lost* event).

Asked to "add Kafka events", a model writes exactly this, because it is what most tutorials show. T3 exists to make it write the other thing. L1 measures the difference.

### 0.1 The twelve rules

1. **Never send to Kafka inside a database transaction that changes state.** Write an outbox row in that transaction; a relay publishes it. L1: the dual write lost 55 and ghosted 181 events out of 10,000; every outbox design lost 0 and ghosted 0. [measured: L1]
2. **Delivery is at-least-once. Make effects idempotent instead of chasing exactly-once.** The relay can crash between the broker acknowledgement and marking the row, and the consumer between applying and acknowledging. Both redeliver. [measured: L1]
3. **An idempotent consumer inserts `(consumer_group, event_id)` into `processed_events` and applies the effect in one local transaction; it acknowledges the offset after.** L1: a naive consumer double-applied 181 of 181 duplicates; the idempotent one, 0. [measured: L1]
4. **The event id is created when the outbox row is written, and never re-generated by the relay.** Otherwise a retry is a new event and dedup can't work. [L1 + practice]
5. **Dedup retention must outlast the longest redelivery window** (relay outage plus consumer lag plus DLT replay). L1: a 2-hour relay outage with 1-hour retention double-applied 83; with 24-hour retention, 0. [measured: L1]
6. **Key records by aggregate id.** A partition preserves order per key, so all of an order's events stay ordered. Ordering across aggregates is not promised and shouldn't be needed. [doc: Kafka]
7. **Multi-instance relays claim rows with `SELECT … FOR UPDATE SKIP LOCKED`.** Two relays then never publish the same row in one claim, and a crashed relay's rows become claimable again when its transaction ends. [doc: PostgreSQL]
8. **Kafka transactions don't replace the outbox.** They make produce and consume-offset atomic *within Kafka*; they don't include your PostgreSQL commit. [doc: Kafka + inference]
9. **Bound retries and classify errors.** Spring Kafka's `DefaultErrorHandler` with exponential back-off, non-retryable exceptions (deserialization, validation) sent straight to the DLT via `DeadLetterPublishingRecoverer`, with the original headers. [doc: Spring Kafka]
10. **A saga is a sequence of local transactions, each publishing through the outbox, each with a compensation, each idempotent by event id.** Orchestrate when the steps need central visibility; choreograph when they are few and stable. [practice]
11. **Resilience4j on synchronous calls inside a saga step:** a time limiter and circuit breaker always, retry only on idempotent calls, and a bulkhead on scarce downstreams. For Boot 4 the starter is `resilience4j-spring-boot4` (2.4.0). [measured: Maven Central]
12. **Propagate `traceparent` from the request through the outbox headers to the Kafka record.** Otherwise the trace ends at the commit, and the slowest part of the flow is invisible. [doc: W3C Trace Context]

## 1. First principles

### 1.1 The crash points, enumerated [inference + L1]

| Design | Crash or failure point | Effect | L1 count (10,000 orders) |
|---|---|---|---|
| A dual write | commit fails after the send | ghost event | 181 |
| A dual write | process dies after commit, before the flush | lost event | 55 |
| Outbox | relay dies after the broker ack, before marking the row | duplicate record (same event id) | 83 |
| Any | consumer dies after the effect, before the ack | redelivery | 98 |
| Naive consumer | any duplicate | effect applied twice (stock reserved twice) | 181 |
| Idempotent consumer, dedup retention shorter than the outage | late duplicate after cleanup | effect applied twice | 83 |

The fault rates are assumptions: 2% rollbacks, 0.5% crash before send, 1% relay crash, 1% consumer crash. Change them, and the counts scale while the *signs* stay the same. Only the outbox loses and ghosts nothing, and only dedup with long enough retention applies exactly once.

### 1.2 The outbox, concretely (what T3 asks for; ⚠ verify the SQL on your PostgreSQL version)

```sql
CREATE TABLE outbox (
  id            bigserial PRIMARY KEY,
  event_id      uuid        NOT NULL UNIQUE,         -- fixed at write time (rule 4)
  aggregate_id  text        NOT NULL,                -- the Kafka record key (rule 6)
  event_type    text        NOT NULL,
  payload       jsonb       NOT NULL,
  headers       jsonb       NOT NULL DEFAULT '{}',   -- traceparent (rule 12)
  created_at    timestamptz NOT NULL DEFAULT now(),
  published_at  timestamptz
);
CREATE INDEX outbox_unpublished ON outbox (id) WHERE published_at IS NULL;   -- the relay's claim query stays small

CREATE TABLE processed_events (
  consumer_group text        NOT NULL,
  event_id       uuid        NOT NULL,
  processed_at   timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (consumer_group, event_id)
);
```

The relay's claim, in one transaction per batch:

```sql
SELECT id, event_id, aggregate_id, event_type, payload, headers
FROM outbox WHERE published_at IS NULL ORDER BY id LIMIT 500 FOR UPDATE SKIP LOCKED;
-- publish each with key = aggregate_id, wait for the acks, then:
UPDATE outbox SET published_at = now() WHERE id = ANY(:ids);
```

Clean up both tables by `created_at`/`processed_at` older than the retention window from rule 5. That window is an ADR decision, not a default.

### 1.3 Polling relay vs CDC [inference]

| | Polling relay | Debezium outbox event router (CDC) |
|---|---|---|
| Moving parts | your service | Kafka Connect + Debezium + logical replication slot |
| Latency | the poll interval (100 ms – 1 s typical) | sub-second, from the WAL |
| Load on the database | the claim query every interval | reads the WAL; no extra queries |
| Failure mode to watch | the relay falls behind (alert on the oldest unpublished row's age) | an unconsumed replication slot keeps WAL and fills the disk |
| Choose when | most services; one team owns it end to end | very high volume, or a platform team already runs Connect |

T3's `relay` variable picks one, and the rest of the template is unchanged. The consumer side is the same either way.

### 1.4 Kafka 4.x and Spring Kafka 4.1 facts the template relies on [doc + measured: BOM]

- **Producer defaults:** since kafka-clients 3.0 the producer defaults to `enable.idempotence=true` and `acks=all`. Idempotence removes producer-retry duplicates *within one producer session*. It does not remove the relay-crash duplicates of rule 2. T3 asks Claude to state these settings explicitly anyway, so a later config change is visible in review.
- **Ordering:** per key, within a partition. With idempotence on, retries keep order for up to five in-flight requests per connection.
- **Versions:** Boot 4.1.2 manages Spring Kafka **4.1.2** and kafka-clients **4.2.2**; let the BOM decide. Kafka 4.x runs without ZooKeeper (KRaft) [research].
- **Error handling:** `DefaultErrorHandler(recoverer, backOff)` with `DeadLetterPublishingRecoverer`. Mark exceptions not retryable with `addNotRetryableExceptions(...)`. A deserialization failure is never transient; send it to the DLT on the first attempt.

### 1.5 Sagas, in one table [practice]

| Step | Local transaction | Publishes (via outbox) | Compensation | Idempotency key |
|---|---|---|---|---|
| 1 Order service | create order PENDING | `OrderPlaced` | cancel order | event id |
| 2 Inventory | reserve stock | `StockReserved` / `StockRejected` | release reservation | `OrderPlaced` event id |
| 3 Payment | authorise | `PaymentAuthorised` / `PaymentDeclined` | void authorisation | `StockReserved` event id |
| 4 Order service | mark CONFIRMED, or compensate | `OrderConfirmed` / `OrderCancelled` | — | each inbound event id |

Each consumer uses rule 3's dedup, so a replayed `OrderPlaced` doesn't reserve twice. Each compensation is itself idempotent: releasing a reservation twice is a no-op. Timeouts are events too: a scheduled "payment timeout" publishes through the outbox like everything else.

### 1.6 Resilience4j for the synchronous edges [doc: Resilience4j + practice]

Inside a saga step, a call to a payment provider is synchronous. Configure it per instance in `application.yml`:
- a **time limiter** (the provider's p99.9 plus a margin);
- a **circuit breaker**;
- a **retry** only if the provider accepts an idempotency key;
- a **bulkhead** sized to what the provider allows you.

An open circuit becomes a `PaymentDeclined{reason=UNAVAILABLE}` event or a retry-later scheduling decision. It never becomes an exception that rolls back the step's local transaction after the provider *did* charge.

## 3. Verified listing

### L1 · `OutboxIdempotencyLab.java`

**What it shows.** 10,000 orders, with seeded faults (deterministic, re-runnable), through five designs:
- A: the dual write;
- B: outbox plus relay, naive consumer;
- C: outbox plus relay, idempotent consumer;
- D: C after a 2-hour relay outage with 1-hour dedup retention;
- E: the same outage with 24-hour retention.

For each it counts committed orders, lost and ghost events, deliveries, duplicate deliveries, double-applied effects, and stock reserved vs expected. It then ties each result to the invariant it demonstrates.

**What it does not show.** Real Kafka or PostgreSQL behaviour: broker failover, rebalances, `SKIP LOCKED` contention, throughput. Those are the Testcontainers tests of §2.2. The lab shows *why* the invariants are the right ones, not that your implementation meets them.

Run: `java OutboxIdempotencyLab.java` (JDK 21+, no dependencies).

```java
// OutboxIdempotencyLab.java - the transactional outbox and the idempotent consumer, measured. A deterministic simulation
// (seeded faults; no broker, no database) pushes 10,000 orders through five designs and counts lost events, ghost events
// (published for a change that rolled back), duplicate deliveries and double-applied effects (stock reserved twice).
// One tick = one order = one second. Fault rates are assumptions; change them and the conclusions keep their sign.
import java.util.ArrayDeque;
import java.util.ArrayList;
import java.util.Comparator;
import java.util.HashMap;
import java.util.HashSet;
import java.util.List;
import java.util.Locale;
import java.util.Map;
import java.util.Set;
import java.util.SplittableRandom;

public final class OutboxIdempotencyLab {
    static final int N = 10_000;
    static final double P_ROLLBACK = 0.02;          // the business transaction fails at commit (constraint, deadlock)
    static final double P_CRASH_BEFORE_SEND = 0.005; // the process dies after commit, before the producer flushes
    static final double P_RELAY_CRASH = 0.01;        // relay dies after the broker ack, before marking the row published
    static final double P_CONSUMER_CRASH = 0.01;     // consumer dies after applying, before acknowledging the offset

    record Delivery(long at, String eventId, int orderId) {}

    record Result(String design, int committed, int lost, int ghost, int deliveries, int duplicates, int doubleApplied,
                  int reserved) {}

    /** A: @Transactional { repo.save(order); kafkaTemplate.send(event); } - the send is outside the database transaction. */
    static Result dualWrite(long seed) {
        SplittableRandom rnd = new SplittableRandom(seed);
        Set<Integer> committed = new HashSet<>();
        List<Delivery> log = new ArrayList<>();
        for (int i = 0; i < N; i++) {
            boolean rollback = rnd.nextDouble() < P_ROLLBACK;
            boolean crash = rnd.nextDouble() < P_CRASH_BEFORE_SEND;
            if (rollback) {
                log.add(new Delivery(i, "evt-" + i, i));          // sent before the commit failed: a ghost event
                continue;
            }
            committed.add(i);
            if (!crash) {
                log.add(new Delivery(i, "evt-" + i, i));          // a crash here instead loses the event
            }
        }
        return consume("A dual write (send inside @Transactional)", committed, log, false, Long.MAX_VALUE, seed + 1);
    }

    /** B-D: order row + outbox row in one transaction; a relay publishes and marks; a crash between them re-publishes. */
    static Result outbox(String design, boolean idempotent, long relayOutage, long retention, long seed) {
        SplittableRandom rnd = new SplittableRandom(seed);
        Set<Integer> committed = new HashSet<>();
        List<Delivery> log = new ArrayList<>();
        for (int i = 0; i < N; i++) {
            if (rnd.nextDouble() < P_ROLLBACK) {
                continue;                                          // rolled back: no order row, no outbox row, no event
            }
            committed.add(i);
            log.add(new Delivery(i + 1, "evt-" + i, i));          // event id fixed at write time (INV-OBX-2)
            if (rnd.nextDouble() < P_RELAY_CRASH) {
                log.add(new Delivery(i + 1 + relayOutage, "evt-" + i, i));   // re-claimed after the relay restarts
            }
        }
        log.sort(Comparator.comparingLong(Delivery::at));
        return consume(design, committed, log, idempotent, retention, seed + 1);
    }

    /** The consumer reserves one unit of stock per event. Idempotent = processed_events insert + effect in one transaction. */
    static Result consume(String design, Set<Integer> committed, List<Delivery> log, boolean idempotent, long retention,
                          long seed) {
        SplittableRandom rnd = new SplittableRandom(seed);
        Map<String, Long> processed = new HashMap<>();             // processed_events: event_id -> processed_at
        ArrayDeque<Map.Entry<Long, String>> byTime = new ArrayDeque<>();
        Map<Integer, Integer> applied = new HashMap<>();
        Set<String> distinctEvents = new HashSet<>();
        Set<Integer> deliveredOrders = new HashSet<>();
        int deliveries = 0;
        for (Delivery d : log) {
            while (!byTime.isEmpty() && byTime.peekFirst().getKey() < d.at() - retention) {   // the retention cleanup job
                Map.Entry<Long, String> old = byTime.pollFirst();
                processed.remove(old.getValue(), old.getKey());
            }
            int attempts = rnd.nextDouble() < P_CONSUMER_CRASH ? 2 : 1;   // crash before ack: delivered again
            for (int a = 0; a < attempts; a++) {
                deliveries++;
                distinctEvents.add(d.eventId());
                deliveredOrders.add(d.orderId());
                if (idempotent && processed.containsKey(d.eventId())) {
                    continue;                                      // duplicate key on insert: skip the effect
                }
                applied.merge(d.orderId(), 1, Integer::sum);
                if (idempotent) {
                    processed.put(d.eventId(), d.at());
                    byTime.addLast(Map.entry(d.at(), d.eventId()));
                }
            }
        }
        int lost = (int) committed.stream().filter(o -> !deliveredOrders.contains(o)).count();
        int ghost = (int) deliveredOrders.stream().filter(o -> !committed.contains(o)).count();
        int doubleApplied = applied.values().stream().mapToInt(n -> Math.max(0, n - 1)).sum();
        int reserved = applied.values().stream().mapToInt(Integer::intValue).sum();
        return new Result(design, committed.size(), lost, ghost, deliveries, deliveries - distinctEvents.size(),
                doubleApplied, reserved);
    }

    public static void main(String[] args) {
        long hour = 3_600;
        List<Result> results = List.of(
                dualWrite(42),
                outbox("B outbox + relay, naive consumer", false, 5, Long.MAX_VALUE, 42),
                outbox("C outbox + relay, idempotent consumer", true, 5, 24 * hour, 42),
                outbox("D C + 2 h relay outage, dedup kept 1 h", true, 2 * hour, hour, 42),
                outbox("E C + 2 h relay outage, dedup kept 24 h", true, 2 * hour, 24 * hour, 42));
        System.out.printf(Locale.ROOT, "%d orders; faults: rollback %.1f%%, crash before send %.1f%%, relay crash %.1f%%, "
                + "consumer crash %.1f%%%n%n", N, P_ROLLBACK * 100, P_CRASH_BEFORE_SEND * 100, P_RELAY_CRASH * 100,
                P_CONSUMER_CRASH * 100);
        System.out.printf(Locale.ROOT, "%-44s %9s %5s %6s %10s %5s %7s %18s%n", "design", "committed", "lost", "ghost",
                "deliveries", "dups", "double", "reserved/expected");
        for (Result r : results) {
            System.out.printf(Locale.ROOT, "%-44s %,9d %5d %6d %,10d %5d %7d %,9d/%,-8d%n", r.design(), r.committed(),
                    r.lost(), r.ghost(), r.deliveries(), r.duplicates(), r.doubleApplied(), r.reserved(), r.committed());
        }
        Result a = results.get(0), b = results.get(1), c = results.get(2), d = results.get(3), e = results.get(4);
        System.out.println();
        System.out.printf(Locale.ROOT, "INV-OBX-1 (no dual write): A loses %d and ghosts %d events; every outbox design loses 0, "
                + "ghosts 0%n", a.lost(), a.ghost());
        System.out.printf(Locale.ROOT, "INV-OBX-3 (dedup + effect in one tx): B double-applies %d of %d duplicates; C %d%n",
                b.doubleApplied(), b.duplicates(), c.doubleApplied());
        System.out.printf(Locale.ROOT, "INV-OBX-6 (retention > redelivery window): 1 h retention vs a 2 h outage double-applies "
                + "%d; 24 h retention %d%n", d.doubleApplied(), e.doubleApplied());
        System.out.println("at-least-once delivery is not the problem: C and E deliver duplicates and still reserve exactly once");
    }
}
```

## 4. Failure modes

| # | Symptom | Root cause | Fix |
|---|---|---|---|
| F1 | Consumers act on orders that don't exist | Send inside `@Transactional`, then the commit failed | Outbox (INV-OBX-1) |
| F2 | Occasional "missing" events after deploys | Process killed after commit, before the producer flush | Outbox |

## 5. Staff-level drills

<details><summary><b>D1 · "Kafka has exactly-once semantics. Why do we need any of this?"</b></summary>

**Naive answer.** Turn on transactions and idempotence, and duplicates disappear.

**Why it fails.** Kafka's exactly-once covers *Kafka to Kafka*: atomically consuming offsets and producing records. Your effect is a PostgreSQL write, and the source of truth for "the order happened" is a PostgreSQL commit. Neither is inside a Kafka transaction.

**Staff answer.** Accept at-least-once delivery and make effects idempotent with a dedup table in the effect's own transaction. That is "effectively once" where it matters. L1 C/E: 181 duplicates delivered, 0 double-applied.
</details>

<details><summary><b>D2 · "How long do we keep <code>processed_events</code>?"</b></summary>

**Staff answer.** Longer than the longest gap between the original delivery and a possible duplicate:

`relay outage you tolerate + max consumer lag + DLT replay delay + safety margin`

Write that arithmetic in the ADR and alert when any term exceeds its budget. L1 D shows what "1 hour, because it seemed enough" costs after a 2-hour outage. Storage is cheap: `(group, uuid, timestamp)` is about 50 bytes.
</details>

<details><summary><b>D3 · "Why should Claude name the failure before fixing it?"</b></summary>

**Staff answer.** Step 1 of T3 ("name the crash points in the current code") is a verification step in disguise.
- If Claude can't name the ghost and lost-event cases in *your* code, it hasn't understood the code, and its outbox will be generic.
- Reviewers can check the list against L1's table in seconds.

It also produces the PR description.
</details>
